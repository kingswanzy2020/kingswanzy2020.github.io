Case study — Kubernetes / GitOps

GitOps deployment pipeline with ArgoCD

I set up a cluster where every change — developer PRs, Renovate's dependency bumps, an image-tag bump from CI — landed in Git first, and ArgoCD was the only thing that ever touched the cluster, reverting anything applied by hand within seconds.

Decommissioned

I tore the cluster down after validation; the Kustomize base, the ArgoCD Application manifest and the sealed secret reproduce it against any cluster with ArgoCD and the sealed-secrets controller installed. Nothing is running now, and everything below is written in the past tense because the cluster is gone, not because it never synced.

What it does

Summary

ArgoCD watched a GitHub repository holding a Kustomize base and a dev overlay, and kept the cluster's actual state in lockstep with whatever that repository said the desired state should be. Developers, Renovate Bot's dependency-bump PRs, and a GitHub Actions workflow that bumped image tags after upstream builds all merged into the same repository — there was no other way to change anything. A PreSync validation Job had to pass before ArgoCD would sync, and a SealedSecret held the database credentials encrypted in Git, decryptable only by the sealed-secrets controller inside the cluster.

How it is wired

The mechanism

Why does everything have to land in Git first? The ArgoCD Application resource points at this repository and has selfHeal: true set, which means ArgoCD doesn't just apply Git's state once — it keeps comparing the live cluster against Git continuously, and reverts anything that doesn't match. kubectl edit against this namespace isn't a way to change something, it's a way to watch ArgoCD undo you within seconds.

Why gate the sync on a PreSync hook instead of just syncing? A PreSync hook is a Job that has to succeed before ArgoCD proceeds with the sync at all. If the validation fails, the whole sync aborts — bad manifests never reach the cluster in a half-applied state, because nothing gets applied yet when the hook runs.

Why SealedSecret instead of a normal Kubernetes Secret? A plain Secret is just base64 — anyone with read access to the repo can decode it. A SealedSecret is encrypted client-side with kubeseal against the cluster's own public key before it's ever committed, and only the sealed-secrets controller running inside that specific cluster holds the private key to decrypt it. That's what makes committing it safe, and it's also why the same sealed file can't be decrypted by pointing it at a different cluster.

Why let Renovate and a CI workflow open PRs alongside developers? Dependency bumps and image-tag updates are exactly the kind of change that's easy to forget to do by hand, and exactly the kind that's safe to automate as long as it still goes through review. Routing all three through pull requests means every change — human or bot — carries the same diff, author, and approval history, and ArgoCD never has to know or care which of the three opened it.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the running system and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

Self-heal reverted a manual scaling change within seconds

I manually scaled the deployment directly against the cluster, bypassing Git entirely. ArgoCD detected the drift and terminated the rogue pod within seconds, restoring the replica count Git declared. That's the actual self-heal result, not a description of what selfHeal: true is supposed to do.

Method Ran kubectl scale directly against the Deployment, then watched kubectl get pods and the Application's sync status until the extra pod was removed and the state matched Git again.

Observed

The committed secret was actually encrypted, not just base64

I opened the committed db-credentials-sealed.yaml in the repository and confirmed it holds a SealedSecret's encrypted blob rather than a plain, base64-encoded Secret — the difference that makes committing it to a public-readable repo safe in the first place.

Method Inspected the committed manifest directly in the Git history.

Observed

All three change sources actually merged as separate, reviewable PRs

Looking back at the repository's PR history, dependency bumps from Renovate and image-tag updates from the GitHub Actions workflow show up as ordinary pull requests with their own diff and merge commit, indistinguishable in kind from a developer's PR — which is the point: ArgoCD syncs from main and never has to know which of the three produced any given commit.

Method Reviewed closed PR history on the repository, checking the author on each (Renovate Bot, the CI bot, and human accounts).

By design

A failing PreSync hook blocks the sync entirely — untested

The Application's sync hooks are configured so a PreSync Job runs before anything else, and a non-zero exit from that Job aborts the sync. I never actually committed a manifest that should fail validation to watch the abort happen, so this is what the hook configuration guarantees, not something I forced and confirmed.

Method Reviewed the PreSync hook annotation and the Job's exit-code contract. Not tested with a deliberately bad manifest.

By design

Only the in-cluster controller can decrypt the SealedSecret — untested

kubeseal encrypts client-side against the cluster's public key, and only the sealed-secrets controller running in that specific cluster holds the matching private key. I didn't attempt to decrypt the committed file from outside that cluster to confirm it actually fails, so I'm stating the guarantee the encryption scheme makes, not a break-attempt I ran.

Method Reviewed the encryption scheme and controller configuration. Not adversarially tested.

Five claims. One measured, two observed, two stated as design properties rather than dressed up as results.
