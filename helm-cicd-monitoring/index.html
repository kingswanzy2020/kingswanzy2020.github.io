Case study — Kubernetes / Observability

Kubernetes CI/CD with Helm and full-stack monitoring

I shipped a small Flask app, FitTrack, to Kubernetes through a four-stage Jenkins pipeline, packaged it as a reusable Helm chart, and put Prometheus and Grafana around it with an alert that only fires when 5xx errors stay above 5% for two full minutes.

Local cluster

This ran on a Kubernetes cluster inside Rancher Desktop on my laptop, not in a cloud account, and nothing was ever exposed publicly. The chart, the Jenkinsfile and monitoring-values.yaml in the repo reproduce it on any cluster with Helm installed. Everything below describes that local run.

What it does

Summary

FitTrack is a multi-page Flask app that exposes a /metrics endpoint with request counts per route. A Jenkins pipeline checked out the code, built the image, pushed it to Docker Hub under both the build number and latest, then ran kubectl set image and waited on rollout status, so a rollout that never converged failed the build. kube-prometheus-stack, installed by Helm with my own values, found the app through a ServiceMonitor, drew it in Grafana, and evaluated a PrometheusRule on the 5xx rate. The app itself was then packaged as its own Helm chart with replicas, image tag and resources templated.

How it is wired

The mechanism

Why a Helm chart instead of the raw manifests? Copy-pasted YAML has no version and no undo. A chart is a set of Go templates; the values fill in the placeholders ({{ .Values }}), and --set or a values file overrides them per environment. Each install is a numbered release, so going back is helm rollback, not working out which YAML was applied last.

Why does the pipeline wait on rollout status? kubectl set image returns as soon as the API server accepts the change, which says nothing about whether new pods ever became ready. Waiting on rollout status makes the Deploy stage fail when the rollout doesn't converge, so a green build means the new version is actually running.

Why does the ServiceMonitor need cross-namespace discovery? The Prometheus Operator only scrapes what a ServiceMonitor selects, and out of the box it only looks at monitors from its own release. I changed that in monitoring-values.yaml so Prometheus discovers monitors in other namespaces too. Without it FitTrack's monitor exists and nothing ever scrapes it.

Why wait two minutes before the alert fires? A single 5xx is a blip, not an incident. The rule fires only when more than 5% of requests return 5xx for two continuous minutes, so a one-off failure never pages anyone. The liveness and readiness probes handle the short-term damage in the meantime: liveness restarts a wedged container, readiness pulls an unready pod out of the Service without restarting it.

What was reachable

Public — nothing; the cluster lived on my laptop and had no ingress.
Internal — FitTrack, Prometheus, Grafana and Alertmanager, all inside the cluster.
Outside it — GitHub and Docker Hub. Jenkins needed a working kubectl context to reach the cluster at all, which turned out to be the hard part.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the running cluster and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Observed

Grafana showed live FitTrack metrics through the ServiceMonitor

Once the cross-namespace discovery setting was in, Prometheus picked up FitTrack's ServiceMonitor and the custom dashboard showed request counts per route coming from the app's own /metrics endpoint — real application data, not just node metrics.

Method Checked the scrape target in Prometheus and the panels on the FitTrack dashboard in Grafana.

Observed

The 5xx alert rule reached the firing state

The PrometheusRule appeared in Prometheus and was captured firing on the error threshold. I'm recording that the rule fired, not a timed measurement of how long detection took — I didn't stopwatch the gap between the first errors and the alert.

Method Read the rule's state in the alerting view (screenshot below).

Observed

A push ended with the new image running, with no manual step

After the kubectl problem below was fixed, a commit went through checkout, build, a push of both tags to Docker Hub, and kubectl set image with rollout status, all from the one pipeline run.

Method Followed the stage view in Jenkins and the Deployment's image tag in the cluster afterwards.

By design

A rollout that never converges fails the build — untested

The Deploy stage waits on rollout status, which exits non-zero if the rollout doesn't complete. I never pushed a deliberately broken image to watch the stage go red, so this is what the stage is built to do, not a failure I forced.

Method Reviewed the Deploy stage in the Jenkinsfile. Not tested with a bad image.

By design

Rollback is one helm rollback — not exercised

Every install of the chart is a numbered release, and the same chart takes per-environment values through --set or a values file. I didn't run a rollback against a bad release here, so I'm claiming the mechanism, not a recovery.

Method Reviewed the chart's templated values and the release history. No rollback was performed.

Five claims. three observed, two stated as design properties rather than dressed up as results.

What actually broke

One failure worth keeping

Jenkins couldn't find kubectl, then couldn't use it against the cluster

Checkout, build and push all went green early. The Deploy stage didn't: Jenkins couldn't discover the kubectl binary, and when it could, it still couldn't execute commands against the cluster. Most of the roughly eight hours went here. It's the least glamorous lesson in the project — a CI server that deploys needs its own working toolchain and its own cluster access, and neither comes for free just because your laptop has them.
