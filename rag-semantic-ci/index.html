Case study — CI/CD / AI

Catching knowledge-base regressions in CI for a RAG API

I wrote a GitHub Actions workflow that rebuilds a RAG API's embeddings and runs semantic tests against what it retrieves, so a push that quietly degrades the knowledge base fails the build — and made those tests deterministic by taking the LLM out of them.

CI workflow

This isn't a hosted service. It's a workflow file in the repo that runs on GitHub's own runners whenever the knowledge base, app.py or the embedding script changes. Everything below describes the runs I triggered while building it.

What it does

Summary

The RAG API retrieves context from a Chroma vector store and asks a local model to answer with it. Ordinary unit tests can't protect that: the code can stay correct while the answers get worse because someone edited a document. The workflow re-embeds every document in docs/, starts the API in mock LLM mode — which returns the raw retrieved context instead of a generated answer — and asserts that known queries still retrieve their expected keywords. A missing keyword fails the build.

How it is wired

The mechanism

Why take the LLM out of the tests? Because it made the tests lie. I removed the word "orchestration" from the knowledge base and kept seeing it in generated answers anyway — the model already knows what Kubernetes is. A test that checks generated text can pass on a broken knowledge base. Mock mode (USE_MOCK_LLM) returns exactly what was retrieved, so the same query gives the same result every run and a missing keyword really means it wasn't retrieved.

Why test retrieval rather than code? In a RAG system the data is part of the product. Semantic tests check that a known question still pulls back the context it should, which is a data-quality check, not a logic check.

Why re-embed in CI instead of committing the vectors? The test has to run against what the documents say now. The workflow runs the embedding script on every run, so an edited document changes the vectors the tests query. When the knowledge base grew to several files, I moved them into docs/ and switched to embed_docs.py, which embeds the whole folder.

Why a path filter? The workflow only has something to say when the knowledge base, app.py or the embedding code changes, so those paths are what trigger it.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the workflow runs and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

Removing a keyword from the knowledge base failed the build

I removed "orchestration" from the Kubernetes document and pushed. The workflow got through checkout, setup, install, rebuilding embeddings and starting the API, then failed at Run semantic tests with AssertionError: Missing 'orchestration' keyword. The degraded document didn't get a green build.

Method Pushed the edited document and read the failing step's log.

Measured

Generated answers hid the regression; retrieved context didn't

With the keyword removed, I queried the API several times in normal mode and still saw "orchestration" in the answers — the model filled it in. In mock mode the retrieved context reflected the edit immediately. That difference is why the tests run against retrieval.

Method Queried /query repeatedly with and without mock mode after editing the document.

Observed

Adding a second document surfaced a failing test straight away

The first run after restructuring into docs/ with a second document passed the Kubernetes query and failed the new one on Missing 'maximus' keyword. That's the run I kept a screenshot of; I'm not claiming a green multi-document run here.

Method Read the job log for the multi-document commit.

By design

Same query, same result

In mock mode the API returns the retrieved text with no sampling involved, so the tests have nothing random in them. I didn't run the suite hundreds of times to measure flakiness; the determinism comes from removing the model, not from a statistic.

Method Reviewed the mock-mode path in app.py.

Four claims. two measured, one observed, one stated as a design property rather than dressed up as a result.

What actually broke

Two failures worth keeping

The model kept saying a word I'd deleted

The first version of the test checked generated answers. I removed "orchestration" from the knowledge base to prove the test would catch it — and the answers still contained it, because tinyllama already knows what Kubernetes is. A test that passes on a broken input is worse than no test. That's where mock mode came from.

The second document failed its first run

When I restructured into docs/ and added a NextWork document with its own test, the Kubernetes query still passed and the new query failed on maximus. That's the suite doing its job on new content: the expected keyword and what the document actually retrieved didn't agree.
