Case study — AWS / Containers

A containerised web app on Elastic Beanstalk

I built a custom nginx image from a three-line Dockerfile, proved it locally, then zipped it up for Elastic Beanstalk and had a live environment in about ten minutes — and shipped an update with one upload.

What it does

Summary

I started with a stock nginx container in detached mode with a port mapping, then wrote a Dockerfile that takes nginx:latest, copies my own index.html over the default page, and exposes port 80. After building and running it locally, I zipped the Dockerfile and page and uploaded them to Elastic Beanstalk, which built the image and ran it on an EC2 instance it manages, behind a public environment URL. To update, I changed the page, re-zipped, and used Upload and deploy.

How it is wired

The mechanism

Why test locally first? If the image doesn't serve the right page on my machine, it won't in the cloud either, and the cloud is the slower place to find out. A container that runs identically everywhere is the whole point; the local run is the cheap proof.

What does Beanstalk take off my hands? The EC2 instances, the health checks, and scaling. I hand it the application; it handles the environment. That's also why an app update doesn't need a new environment — the change is in the code, not the infrastructure.

What are the three Dockerfile lines doing? FROM nginx:latest picks the base, COPY index.html /usr/share/nginx/html/ replaces the default page, and EXPOSE 80 documents the port the container listens on.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the running containers and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

An update shipped with one upload and no environment change

I added an image to index.html, checked it locally, re-zipped, and used Upload and deploy. The live page showed the new content without me touching the environment's configuration.

Method Loaded the environment URL before and after the upload.

Observed

The custom image served my page locally before it went anywhere

The container answered on the host with "Hello from King's custom Docker image!" instead of the nginx welcome page.

Method Opened the mapped port in a browser.

Observed

Upload to live took about ten minutes

Creating the environment, including launch time, took roughly ten minutes before the page served from the Beanstalk URL. That's my reading of the clock during setup, not a timed measurement.

Method Watched the environment until it was healthy, then loaded the URL.

By design

Health checks and scaling are Beanstalk's job

The environment manages its instance, health checks and scaling. I didn't kill the instance or load the app to watch either happen.

Method Reviewed the environment configuration. Not tested.

Four claims. one measured, two observed, one stated as a design property rather than dressed up as a result.

What actually broke

One failure worth keeping

Port 80 was already taken — by me

The first run of my custom image failed because the stock nginx container from earlier was still bound to port 80. docker stop on the old container ID freed it. Small, but it's the difference between understanding container lifecycle and rebooting until things work.
