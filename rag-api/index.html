Case study — AI × DevOps

A RAG API, from a laptop to a container to Kubernetes

I built a retrieval-augmented API with FastAPI, Chroma and a local model, packaged it as a Docker image on Docker Hub, then ran it on Minikube behind a NodePort Service — and deleted the pod to watch Kubernetes replace it while the Service kept routing.

Local cluster

All three stages ran on my machine — a virtualenv, Docker, then a single-node Minikube cluster — with Ollama on the host. The image is public on Docker Hub as ahmed3015/rag-api, and the repo has the app, Dockerfile and manifests. Everything below describes those runs.

What it does

Summary

Stage one was the API: embed.py turns the knowledge base into vectors in Chroma; /query searches them for context, combines it with the question, and asks tinyllama for an answer; /add embeds new content at runtime. Stage two froze the runtime into an image: a Dockerfile on python:3.11-slim that installs the packages, runs the embedding at build time and starts Uvicorn on 0.0.0.0:8000, pushed to Docker Hub and pulled back. Stage three ran that image on Minikube: a Deployment for one replica, a NodePort Service selecting app: rag-api, and Ollama on the host reached through OLLAMA_HOST.

How it is wired

The mechanism

Why retrieval at all? A bare model answers confidently about anything. Asked "What is Kubernetes?", plain tinyllama told me it's a crispy wafer snack with cream and cheese, introduced in Israel in the 1970s. With retrieval, the same model answers from the knowledge base: a container orchestration platform. That before-and-after is the whole argument for RAG.

Why bind Uvicorn to 0.0.0.0 in the container? Inside a container, 127.0.0.1 is the container's own loopback. Binding to all interfaces is what lets a published port, or a Kubernetes Service, reach the API at all.

Why eval $(minikube docker-env)? Minikube runs its own Docker daemon, separate from the one on my host. Pointing my Docker CLI at Minikube's daemon puts the image where the cluster can see it; with imagePullPolicy: Never, the Deployment uses that local image instead of trying a registry.

Why a Service instead of the pod's IP? Pods are replaceable and come back with new IPs. The Service matches pods by label, so when the pod was deleted and replaced, traffic went to the new one without anything being reconfigured.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the cluster and the API's answers and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

Retrieval turned a hallucination into a correct answer

ollama run tinyllama answered "What is Kubernetes?" with a story about a snack food. The same question through /query, grounded in the knowledge base, came back as a container orchestration platform for deploying and scaling containerised applications.

Method Asked the bare model and the API the same question.

Measured

Deleting the pod didn't take the API down for long

I deleted the pod and watched kubectl get pods --watch: the old pod went Terminating to Completed while a new one went Pending, ContainerCreating and Running within about a second. A /query through the Service afterwards answered normally.

Method kubectl delete pod with a watch running, then a curl through the Service URL.

Measured

/add extended the knowledge base at runtime

Posting a sentence about Docker to /add returned {"status": "success", "message": "Content added to knowledge base"} with an ID — no file edits, no re-running embed.py.

Method Called /add from Swagger UI and read the response.

Observed

The image round-tripped through Docker Hub

After pushing, docker pull ahmed3015/rag-api downloaded every layer and the pulled image served the same answers.

Method Pushed, pulled, ran, and queried.

By design

The container behaves the same on any Docker host

Python, the packages and the embedded knowledge base are all in the image. I only ran it on my own machine and Minikube, so portability beyond those is what the image guarantees, not something I tested elsewhere.

Method Reviewed the Dockerfile. Not run on a second machine.

Five claims. three measured, one observed, one stated as a design property rather than dressed up as a result.

What actually broke

Two failures worth keeping

The containerised API wasn't where my browser was looking

The container ran fine, and my first browser attempt at localhost:8000 got Unable to connect. The problem was the URL and port mapping between host and container, not the app — once the published port and the URL agreed, the same /query answered.

500 Internal Server Error from inside the cluster

The API pod started and every query failed: it couldn't reach Ollama on my host. Ollama was listening on 127.0.0.1 only, which nothing outside the host's loopback can reach, and setting OLLAMA_HOST in my shell didn't change the systemd service that actually runs it. Making the service listen on all interfaces, and pointing the pod's OLLAMA_HOST at the host, fixed it. This took most of the four hours.
