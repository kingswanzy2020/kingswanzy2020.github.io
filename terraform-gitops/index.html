Case study — Infrastructure as Code

Terraform GitOps pipeline on AWS

I built a five-module Terraform stack — VPC, EC2, S3, IAM, RDS — where every change went out as a terraform plan reviewed on a pull request, applied only on merge, and authenticated to AWS through GitHub OIDC instead of stored access keys.

Decommissioned

I tore the stack down with terraform destroy after validation; the same GitHub Actions workflow — plan on PR, apply on merge — reproduces it from a clean AWS account. Nothing is live now, and everything below is written in the past tense because the stack is gone, not because it never ran.

What it does

Summary

A five-module Terraform codebase — networking, compute, storage, IAM and RDS — provisioned a full AWS stack from GitHub Actions. Every pull request ran terraform plan and posted the diff for review; merging to main was the only thing that triggered terraform apply. Actions authenticated to AWS by assuming a role through GitHub's own OIDC identity token, so there were no long-lived AWS keys sitting in repository secrets. State lived in S3 with a DynamoDB lock table, and pre-commit hooks caught formatting and validation problems before code was even committed.

How it is wired

The mechanism

Why OIDC instead of stored AWS keys? GitHub Actions exchanges its own OIDC identity token for a short-lived AWS credential by assuming an IAM role — nothing static sits in repository secrets waiting to be rotated or leaked. The trust policy on that role only accepts tokens from this repository's workflows, so a token minted for a different repo can't assume it.

Why split plan and apply across two workflows? The plan workflow runs on every pull request and posts the exact diff terraform apply would make, so a reviewer sees the real change before approving it. The apply workflow only runs on merge to main, which means nothing touches AWS outside of a reviewed pull request — there's no path from an open PR straight to a live resource.

Why does state live in S3 with a DynamoDB lock instead of locally? Local state can't be shared between people or CI runs, and two applies racing against the same file will corrupt it. S3 gives one shared source of truth, and the DynamoDB lock table stops concurrent applies from stepping on each other. I had to provision that bucket and lock table once, by hand, outside Terraform — Terraform can't manage the backend its own state lives in, which is the classic bootstrap problem.

Why IMDSv2 and a scoped RDS security group? IMDSv2 (http_tokens = required) closes the SSRF-to-instance-metadata path that IMDSv1 leaves open — a compromised app process can no longer just curl the metadata endpoint for credentials. And RDS only admits traffic from the EC2 security group instead of a CIDR range, so the database is reachable exactly from the tier that's supposed to talk to it, and from nothing else.

Internal — EC2 reaching RDS on the security-group-scoped path, both inside the VPC's private routing.
Now — nothing. terraform destroy removed the VPC, EC2, RDS and S3 module resources and the IAM role; the S3 backend and DynamoDB lock table survive on purpose — they're the pipeline's own state, not the stack it manages.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the running system and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Observed

The plan-on-PR, apply-on-merge split actually held for every change

Every merge to main in the Actions run history triggered exactly one apply run, and every PR triggered exactly one plan run — no manual workflow dispatch shows up anywhere in the log.

Method Reviewed the Actions run history for both terraform-plan.yml and terraform-apply.yml against the repository's PR and merge history.

Observed

The OIDC token exchange worked with zero static AWS credentials in the repo

The apply job's logs show the credentials step assuming the role via OIDC, and there is no AWS access key anywhere in the repository's secrets.

Method Checked repository secrets for stored AWS keys (none found) and read the OIDC assume-role step in the apply job's logs.

Observed

The backend bootstrap problem was real, and had to be solved by hand

The first terraform init against the S3+DynamoDB backend failed, because the bucket and lock table it points at didn't exist yet. I created just those two resources once via the AWS CLI, outside Terraform, then pointed the backend block at them.

Method Reproduced the failing init, then the working one after the CLI-provisioned backend existed.

By design

RDS is reachable only from the EC2 security group — untested

The RDS module's ingress rule names the EC2 security group as its source rather than a CIDR block. I did not attempt a connection from outside that security group to confirm it's actually refused.

Method Reviewed the security group rule in the Terraform config. Not adversarially tested.

By design

IMDSv2 is enforced against credential theft via SSRF — untested

The compute module sets http_tokens = required, which rejects the older calling convention that SSRF exploits typically rely on to reach instance credentials. I did not run an SSRF proof-of-concept against a live instance to confirm this in practice.

Method Reviewed the launch configuration's metadata options. Not tested against a live exploit.

By design

Concurrent applies can't corrupt state — untested

The DynamoDB lock is acquired by every plan and apply, which should serialize concurrent runs against the same state. I never actually triggered two applies at once to watch the second one block on the lock, so this is what the mechanism guarantees, not something I forced and observed.

Method Reviewed the backend's dynamodb_table locking configuration. No concurrent-run test was performed.

Six claims total. Zero measured — nothing here needed a generated load test — three observed directly, three stated as design properties rather than dressed up as results.

What actually broke

One failure worth keeping

Terraform couldn't manage the backend its own state was supposed to live in

The first terraform init for the S3+DynamoDB backend failed, because the bucket and lock table didn't exist yet — and Terraform can't create the backend it's about to store its own state in without somewhere to put that state first. Fixed by provisioning just those two resources once, by hand, via the AWS CLI, outside Terraform entirely, then pointing the backend block at them. Everything after that point is normal Terraform.
