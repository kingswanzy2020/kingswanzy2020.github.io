Case study — AI × SRE

AI log analysis that opens one incident per error, not one per log line

I built a pipeline where Fluent Bit ships only ERROR and CRITICAL logs out of a Kubernetes cluster, a local LLM diagnoses them, and each new error signature becomes a single GitHub issue with a root cause and a proposed kubectl fix — cached, deduplicated and rate-limited so an error storm can't flood the model or the tracker.

Local cluster

This ran on my own machine: a local Kubernetes cluster for the crashing app and Fluent Bit, with the FastAPI service and Ollama on the host. No cloud API was involved and nothing was public. The repo rebuilds it; everything below describes those runs.

What it does

Summary

A deliberately crash-prone app in the cluster writes structured log lines with a level, a message and a timestamp. Fluent Bit runs as a DaemonSet, keeps only lines whose level matches ERROR or CRITICAL, and POSTs them to a FastAPI service on the host. The service checks Redis for a diagnosis of the same error signature; on a miss, and only within the rate limit, it asks qwen3:1.7b through Ollama for a structured answer — error_category, root_cause, severity, kubectl_fix — caches it, and opens a GitHub issue for signatures it hasn't seen. A Slack alert fires too if a webhook is configured.

How it is wired

The mechanism

Why filter in Fluent Bit and not in the service? Most log lines aren't errors. Dropping them at the DaemonSet means they never cross the network and the model never sees noise. The service filters again, case-insensitively, as a second line.

Why cache by error signature? During an incident the same error repeats hundreds of times. Without a cache, every repeat is another inference call that ties up the model when it's needed most. With the signature as the Redis key, a repeat is answered from cache in milliseconds.

Why deduplicate separately from caching? A cached diagnosis stops repeat model calls; deduplication stops repeat tickets. An error signature that already has an issue is logged and skipped, so one recurring failure is one issue, not a page of them.

Why a rate limit on the model? Each inference takes seconds. A burst of unique errors would queue unbounded calls and exhaust the machine. A token bucket caps how fast the model is asked, whatever arrives.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the running pipeline and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

One real error became one issue, and the repeats didn't

With the crashing app emitting errors, the service received them from Fluent Bit, created a GitHub issue with the signature, root cause and proposed fix, and cached the diagnosis in Redis. Further errors with the same signature were recognised and skipped issue creation.

Method Ran the end-to-end integration test and watched the service log, Redis and the issues repository.

Observed

A pod could reach the service on the host

A throwaway curl pod in the cluster got a JSON response from host.docker.internal:8000/health, which is why that's the address Fluent Bit uses.

Method kubectl run a curl pod against the health endpoint.

By design

A burst of unique errors can't exhaust the machine

A token bucket caps how often the model is called. I didn't generate a deliberate storm of unique errors to watch requests queue.

Method Reviewed the rate limiter. Not load-tested.

By design

The model's answer is a suggestion, not a remediation

The kubectl_fix lands in an issue for a person to read. Nothing in the pipeline runs it.

Method By construction: the service only writes issues and Slack messages.

Four claims. one measured, one observed, two stated as design properties rather than dressed up as results.

What actually broke

Two failures worth keeping

Fluent Bit could see the logs but not the service

The service listened on my host; Fluent Bit ran in a pod. Finding an address a pod could actually reach took trial and error. host.docker.internal:8000 worked, because the server was bound to all interfaces rather than localhost — and I proved it with a curl pod before trusting Fluent Bit to use it.

The first diagnosis was slow for a reason unrelated to the error

Ollama loads the model into memory on first use, which takes 10–30 seconds. Without a warm-up at startup, the first real error of a session waited on that load. The service now warms the model before it needs it.
