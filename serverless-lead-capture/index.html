Case study — AWS / Serverless

A serverless lead-capture site on a real domain

I built an eBook download site for a small business at kahmedt.com: a static site on S3 behind CloudFront over HTTPS, and a form that calls API Gateway and a Lambda function, which emails the owner through SES and stores the lead in DynamoDB.

Decommissioned

This ran in production at kahmedt.com, then I decommissioned it when the project wrapped up. The screenshots document the live system. The site files and the Lambda handler are in the repo; everything below is in the past tense because the infrastructure is gone, not because it never served anyone.

What it does

Summary

A visitor resolved kahmedt.com through Route 53 to CloudFront, which served the static site from S3 over HTTPS with a free ACM certificate. Clicking Download eBook sent an AJAX POST to /epicreads_resource on API Gateway, which invoked the epicreads_contactus Lambda. The function emailed the business owner through SES with the lead's name, email, a UUID and an ISO 8601 timestamp, stored the same item in the ContactMessages table, and logged the run to CloudWatch. Expected load was 10–15 downloads a day, which is why there's no server anywhere in it.

How it is wired

The mechanism

Why serverless for this? The workload was a handful of form submissions a day. An always-on server would cost money while idle and need patching. Lambda and on-demand DynamoDB are billed per request, so at this scale the backend cost is close to zero and there's nothing to patch.

Why CloudFront in front of S3 instead of S3 website hosting? Two reasons. Route 53 can alias straight to an S3 website endpoint only when the bucket name matches the domain, and mine didn't. And CloudFront is what gives the domain HTTPS: the ACM certificate attaches to the distribution, which also caches the site at edge locations.

Why does the certificate live in us-east-1? CloudFront only accepts ACM certificates issued in us-east-1, whatever region everything else is in. My first certificate was in the wrong region and CloudFront wouldn't take it.

Why an inline policy on the Lambda role? The function needs exactly two things: ses:SendEmail and dynamodb:PutItem. An inline policy scoped to those is deleted with the role, so nothing outlives the function.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the live system and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

One click produced an email and a stored lead

I submitted the download form on the live site. The owner's inbox got an email with the full name, email address, a UUID and an ISO 8601 timestamp, and the same item appeared in ContactMessages. The first version of the email had fewer fields; the metadata came with the DynamoDB phase.

Method Submitted the form, then checked the inbox and the table.

Observed

The site served at the custom domain over HTTPS

kahmedt.com loaded through CloudFront with a valid certificate, once the certificate was in the right region and the registrar pointed at Route 53.

Method Loaded the domain in a browser and checked the certificate (screenshot below).

Observed

Every invocation showed up in CloudWatch

CloudWatch had the Lambda function's runs and the API Gateway metrics, which is where the CORS and permission failures below were diagnosed.

Method Read the function's log group and metrics.

By design

The function can do two things and nothing else

The execution role's inline policy allows dynamodb:PutItem and ses:SendEmail. I didn't try to make the function call anything else to watch it fail.

Method Reviewed the inline policy. Not adversarially tested.

By design

Idle cost is close to zero

Lambda is billed per invocation and the table is on-demand, so with 10–15 submissions a day there's no standing compute cost. That's the pricing model, not a bill I'm quoting.

Method Reasoned from the services' pricing models; no cost report kept.

Five claims. one measured, two observed, two stated as design properties rather than dressed up as results.

What actually broke

Four failures worth keeping

CloudFront rejected my certificate

I requested the ACM certificate in my working region. CloudFront only uses certificates from us-east-1, so it simply wasn't offered. Re-issuing it in us-east-1 fixed it.

The domain didn't resolve to anything I'd built

The Route 53 hosted zone had records, but the registrar was still using its own nameservers. Copying all four NS records from the hosted zone to the registrar is what made Route 53 authoritative.

CORS errors on submit

The form's AJAX call from the CloudFront domain was blocked by the browser because API Gateway wasn't returning CORS headers. I enabled CORS on the resource and had the Lambda return Access-Control-Allow-Origin as well.

Lambda couldn't write to DynamoDB

The function ran, sent the email, and failed on the write: its role had no DynamoDB permission. An inline dynamodb:PutItem policy on the execution role fixed it, scoped to exactly that action.
