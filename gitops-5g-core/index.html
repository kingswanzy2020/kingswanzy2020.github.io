Case study — Kubernetes / GitOps

A GitOps-driven 5G core on Kubernetes

I ran an Open5GS 5G standalone core as cloud-native network functions, where adding a network slice is a two-line Git commit: ArgoCD applies it, and the Open5GS Operator turns it into running config.

Local cluster

This ran on the Kubernetes cluster built into Docker Desktop on my machine, with no radio side attached — no gNB or UE simulator, so no device ever registered. The repo's three ArgoCD Applications rebuild it on any cluster with ArgoCD installed. Everything below describes that local core.

What it does

Summary

One Git repository, telco-platform-gitops, describes the whole core: kube-prometheus-stack, the Open5GS Operator, the Open5GS custom resource with its PLMN (999/70), TAC and slices, an Open5GSUser subscriber, and the wiring that lets Prometheus scrape the Operator itself. ArgoCD syncs three Applications from it. The Operator reconciles the one Open5GS resource into eleven network functions plus MongoDB, and rewrites only the config a change touches. Prometheus scrapes the AMF, PCF and UPF, and the Operator's own reconcile metrics, into Grafana.

How it is wired

The mechanism

Why an Operator instead of raw manifests? The core is a single Open5GS custom resource: PLMN, TAC, and a list of slices. The Operator owns translating that into the individual Deployments and ConfigMaps for every network function. A slice change becomes a two-line diff to that resource instead of hand-editing NF config files, and the reconcile loop keeps the live functions matching it.

Why three ArgoCD Applications, synced in order? observability (kube-prometheus-stack), open5gs-operator (Gradiant's chart, 1.0.7) and open5gs-cr (this repo's overlays/local) are separate Applications. Observability goes first because the Operator can only create ServiceMonitor objects once that CRD exists.

Why eleven network functions and not seven? The track focuses on the seven headline 5G SA functions — AMF, SMF, UPF, NRF, UDM, AUSF, PCF — which is where my first count of 7 + MongoDB came from. The Operator also enables NSSF, BSF, SCP and UDR by default. They were already running before the second slice existed: ArgoCD showed the BSF ConfigMap two hours old right after the slice sync.

Why scrape the Operator as well as the functions? "Pods are running" says little about whether a change was reconciled. A separate base adds a ServiceMonitor for the controller-manager plus a ClusterRoleBinding so Prometheus's ServiceAccount passes kube-rbac-proxy's SubjectAccessReview. With controller_runtime_reconcile_total available, reconciliation is read directly instead of guessed from restarts. On the functions, metrics are enabled only on the AMF, PCF and UPF — registration, policy and data-plane state.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the running system and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

A new slice went from commit to Sync OK in about two minutes

Commit 5907f0e added a URLLC-style slice (SST 2, SD 0x222222) next to the existing SST 1 / SD 0x111111 at 02:20. ArgoCD reported Sync OK to that commit at 02:22:01. The slice added no pods — it landed as new config on two functions.

Method Compared the commit time against the sync time on the open5gs-cr Application, and checked which ConfigMaps changed.

Observed

All three Applications were Healthy and Synced

observability, open5gs-cr and open5gs-operator all showed Healthy and Synced, with eleven network functions plus MongoDB running from one Open5GS resource.

Method Read the Application tiles in the ArgoCD UI.

Observed

Prometheus scraped the AMF, PCF and UPF, and the Operator's reconcile rate was visible

All three ServiceMonitor targets showed UP with a scrape duration of 1 ms each. After the metrics commit landed, the reconcile rate for controller="open5gs" appeared at about 0.1/s.

Method Filtered Prometheus target health to open5gs; read the reconcile panel in Grafana.

By design

Every core change goes through Git — by practice, not enforcement

In this build, every change to the core is a commit in the repo's history; I didn't run kubectl apply for core config. That's how I worked, not a lock: the Applications don't forbid a manual edit, so I'm stating the practice rather than claiming it couldn't happen.

Method Reviewed the repo history against the changes made. No admission policy enforces it.

By design

The metric pipeline works; traffic was never tested

The AMF and UPF session panels read 0 because no device registered. The dashboards prove metrics flow from the functions to Grafana, not that the core carries sessions.

Method No gNB or UE simulator was attached.

Five claims. one measured, two observed, two stated as design properties rather than dressed up as results.

What actually broke

Three failures worth keeping

ImagePullBackOff on the Operator

Chart 1.0.5 pulled kube-rbac-proxy from gcr.io/kubebuilder, a registry path that has been retired. The first fix overrode the image to quay.io/brancz/kube-rbac-proxy:v0.18.1 in the Application's Helm values. Moving to chart 1.0.7 made the override unnecessary, so it came back out.

Permanently OutOfSync while every pod was healthy

The custom resource set serviceMonitor: true at the top of spec. The CRD has no such field there — it's per network function — so the API server's structural-schema pruning silently dropped it on every apply. Git always had a field the live object never kept, and ArgoCD kept reporting drift. Moving the flag under amf:, pcf: and upf: fixed the drift and turned the scrape targets on. Most of the three hours went here.

The Application pointed at a placeholder repo

The first open5gs-cr Application still said YOURUSER/telco-gitops.git and targeted base/ directly, while overlays/local listed raw YAML files instead of Kustomize bases. The restructure (3b06c11) pointed it at the real repo and the overlay, and turned each base into a proper Kustomization.
