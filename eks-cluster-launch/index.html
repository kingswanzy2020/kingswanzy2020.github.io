Case study — Kubernetes / AWS

Launching an Amazon EKS cluster with eksctl

I created a managed Kubernetes cluster on Amazon EKS with one eksctl command, mapped my IAM user into Kubernetes RBAC with an access entry, then terminated the worker nodes on purpose to watch the node group put them back.

Guided lab

I built this in my own AWS account as a guided NextWork lab. I'm not pointing you at a live endpoint — the screenshots below were captured during the build, and the one eksctl create cluster command shown below recreates the cluster and both CloudFormation stacks. Everything below is in the past tense for that reason.

What it does

Summary

From an EC2 instance I used as an admin box, I ran eksctl create cluster with the cluster name, a node group of three t3.micro nodes (minimum 1, maximum 3), Kubernetes 1.33 and the ap-northeast-1 region. eksctl handed that to CloudFormation as two stacks: one for the control plane and its VPC networking, one for the node group. The EKS console wouldn't show me the nodes until I added an IAM access entry mapping my IAM user to AmazonEKSClusterAdminPolicy. Then I terminated node instances directly in EC2 and watched replacements launch.

How it is wired

The mechanism

Why eksctl instead of building the pieces by hand? A working cluster needs a control plane, a VPC with the right subnets and routes, IAM roles, and worker nodes that know how to join. eksctl takes one declarative command and turns it into CloudFormation stacks, so every resource it made is traceable to a stack and deletable with it.

Why two stacks? The cluster stack holds the control plane and the networking the pods and nodes need to talk to each other. The node group stack holds the EC2 instances that actually run pods. Keeping them separate means the node group can be changed or replaced without touching the control plane.

Why did I need an access entry when I already had an AWS admin login? Kubernetes has its own permission model. Being allowed to call the EKS API doesn't make my IAM user a Kubernetes user. An access entry maps the IAM identity into the cluster's RBAC; with AmazonEKSClusterAdminPolicy attached, the console could finally list the nodes.

What actually replaced the nodes I deleted? The node group's desired size was three. When I terminated instances in EC2, the gap between desired and actual showed up and the node group's Auto Scaling group launched replacements, which joined the cluster on their own. That's the same desired-state idea Kubernetes uses for pods, applied one level down to the machines.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the running system and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

Terminated nodes were replaced without me doing anything

I terminated node-group instances directly in the EC2 console. The instance list then showed the terminated ones next to new instances already Running with their status checks passed, back at three — the node group's desired size.

Method Terminated instances in EC2, then watched the instance list until the replacements were Running.

Observed

One command produced both stacks and a three-node cluster

The node group stack reached CREATE_COMPLETE, and the EKS console showed nextwork-eks-cluster on Kubernetes 1.33 with three nodes, all Ready. It took about an hour including setup and reading, which is mostly waiting on CloudFormation.

Method Read the CloudFormation stack status and the cluster's Compute tab.

Observed

The console couldn't see the nodes until the access entry existed

Before the access entry, the EKS console wouldn't show node details even though I was signed in as an AWS admin. After mapping my IAM user to AmazonEKSClusterAdminPolicy, the nodes appeared.

Method Checked the Compute tab before and after creating the access entry.

By design

Every resource is traceable to a stack

Because eksctl went through CloudFormation, the VPC, the roles and the instances all belong to one of two stacks and go away with them. I'm stating that from how the stacks are built; I didn't audit every resource against the stack lists.

Method Reviewed the two stacks' resource lists at a high level.

Four claims. one measured, two observed, one stated as a design property rather than dressed up as a result.

What actually broke

One failure worth keeping

eksctl: command not found, then no permission to use it

The first eksctl create cluster failed because the tool simply wasn't installed on the admin instance. Once it was, the next run failed because the instance had no credentials allowed to create an EKS cluster. Two failures, neither of them Kubernetes — the tool and the identity running it have to exist before any of the interesting parts can.
