Case study — AWS / Security

Tag-based least privilege for EC2 with IAM

I wrote an IAM policy that lets developers do anything to EC2 instances tagged development, only look at everything else, and never create or delete tags — then signed in as that developer to try stopping both instances.

Guided lab

I built this in my own AWS account as a guided NextWork lab. I'm not pointing you at a live endpoint — the screenshots below were captured during the build, and the JSON policy and two tagged instances recreate it. Everything below is in the past tense for that reason.

What it does

Summary

Two EC2 instances got an Env tag: production and development. NextWorkDevEnvironmentPolicy has three statements: allow ec2:* where ec2:ResourceTag/Env is development; allow ec2:Describe* on everything; deny ec2:CreateTags and ec2:DeleteTags. The policy is attached to a user group, a developer user is in the group, and the account has an alias so that user signs in at a readable URL. I tested it twice: as the user in the console, and in the IAM Policy Simulator.

How it is wired

The mechanism

Why tags instead of listing instance IDs? A tag makes the boundary a property of the resource. A new development instance is covered the moment it's tagged; nobody has to edit the policy.

Why deny tag changes outright? If a developer could edit tags, they could tag a production instance development and the first statement would hand them control of it. An explicit Deny on CreateTags and DeleteTags closes that, and an explicit Deny can't be overridden by any Allow.

Why attach to a group? So the policy describes a role, not a person. Onboarding a developer is adding them to the group.

Why was stopping production denied, exactly? Not by the Deny statement. The only Allow for StopInstances carries the development tag condition, so for a production instance no statement allows it — an implicit deny. The console's error said exactly that: no identity-based policy allows the action.

What the developer could do

Development — anything EC2 allows on instances tagged Env = development.
Everything else in EC2 — Describe* only.
Never — create or delete tags, or anything outside EC2 — most console panels showed Access Denied.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the console as the developer and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

Stopping production was refused; stopping development worked

Signed in as the developer, I tried to stop the production instance and got an error saying the user isn't authorized to perform ec2:StopInstances because no identity-based policy allows it. Stopping the development instance went straight through.

Method Attempted both stops in the EC2 console as the restricted user.

Measured

The simulator needed the tag in context to show the Allow

With the resource left as *, the simulator returned StopInstances as implicitly denied (no matching statements) and DeleteTags as denied by one matching statement. Adding ec2:ResourceTag/Env = development to the simulation context turned StopInstances into allowed.

Method Ran both actions in the IAM Policy Simulator, with and without the tag condition key in context.

Observed

Everything outside the policy defaulted to Access Denied

Logged in as the developer, most dashboard panels showed Access Denied: anything the policy doesn't mention is denied by default.

Method Browsed the console as the restricted user.

By design

A developer can't tag their way into production

The explicit Deny on CreateTags and DeleteTags applies to every EC2 resource, and explicit Deny wins over any Allow. The simulator showed DeleteTags denied; I didn't try re-tagging the production instance as the user.

Method Policy Simulator for DeleteTags; no live re-tag attempt.

Four claims. two measured, one observed, one stated as a design property rather than dressed up as a result.

What actually broke

One failure worth keeping

I misread why the simulator said denied

My first simulation of StopInstances came back denied, and I put it down to the Deny statement overriding the Allow. The simulator's own detail says something else: implicitly denied, no matching statements. With the resource set to * and no tag in the context, the Allow's condition can't match. Once I gave the simulation ec2:ResourceTag/Env = development, it showed allowed. The lesson stuck better than the policy did: read which kind of deny you got.
