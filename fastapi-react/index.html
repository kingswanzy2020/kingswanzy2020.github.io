Case study — Kubernetes / CI/CD

A FastAPI + React template, taken from compose to Kubernetes

I took an existing full-stack template that only ran under docker-compose and built the whole delivery path around it — production images, Terraform, Ansible, one Helm chart, a GitHub Actions pipeline — then shipped a broken change on purpose to see whether any of it held.

Decommissioned

I destroyed the EC2 host and the EKS cluster after validating them, and the local kind release is uninstalled; EKS_ENABLED is back to false, so the pipeline's push and deploy jobs skip. The same Terraform, chart and workflows rebuild all of it. Everything below is in the past tense because the environments are gone, not because they never ran.

What it does

Summary

The starting point was someone else's template: a FastAPI backend with a Celery worker, Postgres, Redis as the broker and a React frontend behind nginx, started with one script. I didn't write the application; the work here is everything between that and a deploy I could trace and undo. That happened in two passes. The first built production images, provisioned a VPC, an EC2 host, RDS and ECR with Terraform, and configured and deployed the host with Ansible. The second moved the app to Kubernetes: one Helm chart on a three-node kind cluster, failure drills against it, a CI/CD pipeline, and images named after the commit they were built from. EKS came last, as a same-day run of the pieces a laptop can't show — the ALB, IRSA, External Secrets and RDS — and was destroyed afterwards.

How it is wired

The mechanism

Why a local cluster first and EKS last? Each kind node runs a real kubelet, so a rolling update, a PodDisruptionBudget or a drain behaves there the way it does on EKS, and it costs nothing to break. EKS with a NAT gateway, an ALB, nodes and RDS ran at roughly $0.30–0.35 an hour, so I only used it for what kind can't reproduce. The chart is the same in both places; only the values file changes, and the ingress class goes from traefik to alb.

Why do readiness and liveness hit different endpoints? Readiness runs SELECT 1 and opens a broker connection, and returns 503 if either fails, so a pod that can't reach its dependencies leaves the Service. Liveness checks nothing outside the process. If both checked the database, a short Postgres outage would restart every backend pod at once and turn a blip into an outage.

Why are migrations a Helm hook and not an initContainer? An initContainer runs once per pod, so two replicas would race to migrate. The hook runs Alembic once per release, before any Deployment changes; if it fails, the release fails and the old pods are untouched. The cost is that every migration has to work with the previous release's code, because a rollback puts the old code back but leaves the schema where it is.

Why is the full git SHA the only deployable tag? With latest, pods started at different times can run different code and nothing in kubectl describe says which. Here the build bakes the commit into the image, the tag is sha- plus all 40 characters, ECR refuses to overwrite a tag, and /api/v1/version returns the commit from the running process. A rollback target is then a name that can only ever mean one build.

Why two IAM roles for one pipeline? Pull requests run everything on a kind cluster inside the runner and never see a cloud credential. On main, the push role is trusted for the branch and can only write to ECR; the deploy role is trusted for the dev GitHub environment and maps to a Kubernetes Role in one namespace. Both are assumed through OIDC, so there's no access key in the repository to leak.

What was reachable

Public — port 80 on the EC2 Elastic IP, then the ALB on EKS. HTTP only; neither had TLS.
Internal — backend, worker, Redis and the database. On EC2 their ports weren't published; RDS sat in private subnets and admitted only the app's security group.
Now — nothing. Both AWS environments are destroyed and the local release is uninstalled.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the running system and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

A release that couldn't start never took traffic, and one command undid it

I deployed a tag that only existed for the backend image. The new web pod sat in ImagePullBackOff, Helm recorded the revision as failed, and the old ReplicaSets stayed at 2/2 because the rollout allows zero unavailable pods. /api/v1/version kept returning the previous commit the whole time. helm rollback then put the release back on a good revision, and after the next deploy the endpoint matched git rev-parse HEAD.

Method deploy-local.sh --skip-build --no-atomic -- --set image.tag=sha-deadbeef so the failure stayed in place, then kubectl get rs, kubectl describe pod, a curl of the version endpoint, helm rollback and helm history.

Measured

Broken code merged to main did not deploy

I merged a pull request with a syntax error in the backend. cd.yml reran the tests on main, lint and backend failed, and build-push and deploy were skipped. Nothing stopped the merge itself, though: the PR went in with 2 of 4 checks passing, because the branch has no required status checks. The gate that held was in the deploy pipeline, not on the branch.

Method Merged PR #3 with failing checks and read the CD run that followed: test failed, build-push and deploy skipped.

Measured

Every pull request proves the chart can roll itself back

The chart-test job installs the chart on a kind cluster in the runner, smoke-tests readiness, then forces an upgrade that can't succeed. The run I captured shows revision 2 failed, revision 3 as "Rollback to 1", and the backend back on its original SHA. The job only passes if that happens.

Method Read the chart-test job log on PR #1: the helm history it prints after the forced failure, and the image the Deployment ended on.

Measured

The backend autoscaled to its ceiling under load, then came back down

With a floor of 2, a ceiling of 6 and a 70% CPU target, the HPA went from 2 to 4 to 6 replicas within about a minute of the load starting, and returned to 2 about five minutes after it stopped, which is the 300-second stabilisation window. CPU was still several times over target at 6 replicas, so the ceiling is what stopped it, not the demand. The percentages are against a 100m request on a laptop cluster; they show the mechanism working, not a capacity figure.

Method hey -z 3m -c 50 http://localhost/api/v1 against the local cluster while watching kubectl get hpa -w.

Measured

Draining a node moved the stateless pods and took the API down with the database

Draining one worker rescheduled web, worker and backend onto the other. Postgres did not move: its volume is pinned to the drained node, so the pod stayed Pending until I uncordoned it. The backend pods were running but showed 0/1 ready, because readiness checks the database, so the UI loaded and the API didn't. That's the probe doing its job, and it's also the reason Postgres goes to RDS on EKS.

Method kubectl drain desktop-worker2 --ignore-daemonsets --delete-emptydir-data, then kubectl get pods -o wide before and after kubectl uncordon.

Observed

On EKS, the running app, the Deployment and the pods all named the same commit

After a deploy from main, /api/v1/version through the ALB returned the full commit hash, the Deployment's image was that hash with the sha- prefix, and both backend pods reported the same image digest.

Method Curled the version endpoint on the ALB hostname and compared it with kubectl get deploy and the pods' imageID.

Observed

Terraform was idempotent on EC2; the Ansible converge was not quite

A second terraform apply reported no changes. A second run of the Ansible playbook reported changed=1, not 0: at that stage the EC2 path still deployed latest with pull-always, so the pull task reports a change on every run. Passing a fixed SHA to the deploy playbook removes it; I didn't go back and capture a clean changed=0.

Method Ran each tool twice against the unchanged dev environment and read the plan summary and the play recap.

Observed

The image scan reports; it does not gate

Trivy found 51 fixable HIGH or CRITICAL findings in the backend image's OS packages and 39 in its Python packages, most of them from the template's Python 3.8 base and 2020-era pins. I left the scan writing to the job summary instead of failing the build, since a gate that is red from day one gets ignored. Those findings are still open.

Method Read the Trivy summary on the CD run for commit 681be8a.

By design

A rollback is safe across a schema change — untested

Because the migration hook runs before the new code and a rollback doesn't reverse it, migrations have to be written expand-then-contract: add the column in one release, switch to it in the next, drop the old one after that. The chart enforces the ordering. No release in this project changed the schema, so I never rolled back across one.

Method Reviewed the hook annotations on the migrate Job. No rollback was run across a migration.

By design

The pipeline's AWS access is scoped per job — not adversarially tested

The push role trusts only main and can only write to ECR; the deploy role trusts only the dev environment and is bound to a Role in one namespace; the ECR repositories are immutable. I saw the roles work for their own jobs. I didn't try to assume one from a different branch, deploy outside the namespace, or push over an existing tag.

Method Reviewed the trust policies, the EKS access entry and the repository settings in Terraform.

Ten claims total. Five measured, three observed, two stated as design properties rather than dressed up as results.

What actually broke

Five failures worth keeping

build-push failed with Not authorized to perform sts:AssumeRoleWithWebIdentity

Both CI roles trusted the name-based subject, repo:<owner>/<repo>:…, with StringEquals. This repository issues immutable OIDC subjects that embed the owner and repository IDs, so the token never matched and the action retried twelve times before giving up. Fixed by building both trust subjects from a prefix variable set to what GitHub actually reports for the repository.

The backend couldn't log in to RDS with a password that was correct in Secrets Manager

The RDS-generated master password contained a $. The deploy script wrote it into .env, and compose treated the $ as the start of a variable and expanded it to nothing, so the password that reached the container was shorter than the real one. The fix is to write it as $$, and my first attempt broke it a second way: inside a bash substitution an unescaped $$ is the shell's own PID, so the password got a process ID spliced into it. Escaping it as \$\$ got the literal pair into the file.

The frontend container went unhealthy while serving every request correctly

The HEALTHCHECK ran wget http://localhost/. Inside the container localhost resolved to ::1 first, my nginx config only listened on IPv4, and wget didn't fall back, so the probe was refused every 30 seconds. Real traffic arrived on the container's IPv4 address and was fine. Fixed by probing 127.0.0.1.

The Ansible dry run failed on a host that had never been converged

--check --diff simulates creating the deploy user, then fails on the next task that changes ownership to a user that doesn't exist yet. A dry run previews a change to a host that's already been converged; it can't stand in for the first run. I ran the playbook for real once and used --check after that.

The CI lint job failed before linting anything: ansible-lint 26.9.0 depends on black>=25.2.0

The workflow pinned black==24.2.0 to match the backend's formatter and installed ansible-lint into the same environment, and pip couldn't satisfy both. Fixed by giving ansible-lint its own virtualenv under $RUNNER_TEMP and putting that on the PATH for its step only.
