DORA delivery scoreboard with DuckDB

I built a scoreboard that computes four DORA metrics straight from timestamps as named SQL blocks, and refuses to publish the fifth — rework rate — until an AI classifier's labels reproduce 18 of 20 hand-audited judgments, with a stated limitation printed on every card.

Local script, not a service

This never was a deployed service — it's a script you run against a captured corpus. python scoreboard.py reproduces the exact run below in about a minute, no cluster or cloud account involved. Everything here describes that one-shot run, not something that's currently “live” or “down.”

What it does

Summary

scoreboard.py loads a captured corpus of 20 deploys, 4 incidents and 20 hand-audited labels into in-memory DuckDB tables, and computes four DORA metrics as named SQL blocks — deployment frequency, change lead time, change fail rate, and failed-deployment recovery time. The fifth metric, rework rate, needs a judgment call no timestamp encodes, so it sits behind a gate: an AI classifier labels all 20 deploys, and the metric only gets released if those labels reproduce at least 18 of the 20 sealed ground-truth labels and cover every deploy. A failed or missing gate prints WITHHELD with a reason instead of guessing. Everything renders into one self-contained scoreboard.html with no external requests.

How it is wired

The mechanism

Why are the metrics SQL blocks instead of Python functions? Each block in metrics.sql is headed by Counts, Excludes and Does not prove comments, so reviewing a metric means reading a SELECT, not tracing loop state and accumulators across a Python file. The runner pulls the block's name from its first comment line, so adding a metric needs no code change — just a new block.

Why medians instead of averages, and distinct deploys instead of raw incident counts? A mean lets one pathological deploy — say, a lead time of 400 hours during a bad week — drag the headline number away from what's typical. A median doesn't move for that. And counting distinct deploys rather than incidents means a single deploy that causes two incidents still counts as one failed deploy, not two — otherwise the fail-rate denominator and numerator would be measuring different things.

Why does the gate check coverage as well as accuracy? Accuracy alone is gameable: a classifier that abstains on every hard case and only answers the easy ones can post 18 or more correct out of a smaller answered set while being useless exactly where judgment actually matters. Requiring a prediction for all 20 sealed deploys — not just 18 correct ones — removes selective abstention as a way to pass. Both edges are pinned by tests: 18 correct passes, 17 fails, and 19 perfect answers out of 20 deploys still fails on coverage alone.

Why print WITHHELD instead of a rough estimate? A number with a confidence caveat still gets read as a number. WITHHELD plus the specific reason — the score achieved and the bar it missed — can't be misread as a measurement. There's no fallback value and no partial figure sitting behind it.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the output and saw the state it was already in. By design means the logic guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

The AI gate actually blocks the metric when there's nothing to score

Running python scoreboard.py with no data/ai_labels.json present printed rework_rate: WITHHELD (no AI labels found) — the gate doing exactly what it's supposed to do with nothing to compare against. Adding the labels file back and re-running scored 20 of 20 sealed labels reproduced with full coverage, and released rework rate at 15.0%.

Method Ran scoreboard.py twice — once with data/ai_labels.json moved aside, once restored — and read the printed slot value both times.

Measured

18/20 passes, 17/20 fails, and 19 perfect-but-incomplete answers still fails

The gate's two boundary tests assert exactly this: a run scoring 18 of 20 correct with full coverage passes; 17 of 20 fails; and a classifier that only answers 19 of the 20 deploys — even if all 19 are correct — fails on coverage regardless of accuracy. I ran the suite and watched these three specific cases resolve the way the gate is supposed to.

Method python -m unittest tests.test_scoreboard.GateTest — the accuracy-boundary and coverage-boundary tests specifically.

Observed

24 of 31 tests pass at the published commit — and the other 7 failures are explainable

Two test classes predate the last two data commits. SqlParserTest still expects four SQL blocks, but metrics.sql now carries a fifth (rework_rate) once the gate started passing. StdoutContractTest asserts ai_labels.json is absent so it can pin the exact withheld line — but the labels are now committed, which is what lets the metric release at all. Moving the labels file aside brings the suite to 29 of 31. This is drift between the tests and the data, not a broken feature.

Method Ran the full suite and read each of the 7 failing assertions against the current state of data/.

Observed

The rendered page's own caveats don't fully match its content requirements yet

A SQL recount confirmed all five printed values were correct, but reviewing the actual scoreboard.html against what it's supposed to say found three gaps: it doesn't name report supersession or the retired DORA performance tiers, it skips the untested data-transport assumption and the volatility of a single 30-day window, and there's no explicit “what this does not fix” section on the page itself. The numbers are right; the caveats around them are incomplete.

Method Cross-checked scoreboard.html's rendered content against the documented caveat requirements in docs/.

By design

Deployment frequency and change fail rate can't detect what they don't record — untested

Deployment frequency counts pipeline events, not confirmed user-facing releases — a deploy that silently failed to reach users still counts. Change fail rate only counts incidents that were noticed and attributed back to a specific deploy; an unnoticed regression contributes to neither. These are stated limits of what a timestamp-only pipeline can know, not something I stress-tested against a real undetected failure.

Method Read directly from each metric's own Does not prove block in metrics.sql. Not tested against a real incident.

What actually broke

Three failures worth keeping

The gate withheld the metric because the inspector never arrived

The first full run printed rework_rate: WITHHELD (no AI labels found). That's not a bug — it's the gate doing its job: with no ai_labels.json there's nothing to score against the sealed set, so the slot holds instead of guessing. Once the AI labels were committed, the gate scored 20/20 with full coverage and released 15.0%.

The numbers passed their audit; the caveats didn't

A SQL recount confirmed all five values, but reviewing scoreboard.html against its own content requirements found three gaps — no mention of report supersession or the retired DORA performance tiers, no acknowledgment of the untested data-transport assumption or the volatility of a 30-day window, and no explicit “what this does not fix” section. For a readout whose entire point is its caveats, correct numbers with incomplete limits is still a defect.

The test suite drifted behind the last two data commits — 24 of 31 pass

SqlParserTest still expects four SQL blocks after rework_rate became a fifth, and that block queries deploy_labels, a table that only exists once the gate has passed. StdoutContractTest asserts ai_labels.json is absent so it can pin the exact withheld line — but committing the labels is what released the metric in the first place. Moving the file aside gets the suite to 29 of 31. The tests encode an intent — the default run demonstrates withholding — that the committed corpus has since moved past.
