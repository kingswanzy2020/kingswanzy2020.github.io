Case study — AWS / Serverless

A three-tier web architecture with no servers in any tier

I built the classic three-tier pattern as three serverless modules — a frontend delivered by CloudFront from a private bucket, an API Gateway and Lambda logic tier, and a DynamoDB data tier — and locked each one down to what the tier next to it needs.

Guided lab

I built this in my own AWS account as a guided NextWork lab. I'm not pointing you at a live endpoint — the screenshots below were captured during the build, and the static site, the Lambda handler and the exported API definition in the repo rebuild the three tiers. Everything below is in the past tense for that reason.

What it does

Summary

The presentation tier is index.html, style.css and script.js in a private S3 bucket, served only through a CloudFront distribution with Origin Access Control. The logic tier is a REST API in API Gateway, deployed to a prod stage, in front of a Lambda function that reads userId from queryStringParameters and returns 200 with the user or 404 with an error. The data tier is a DynamoDB table keyed on userId. The three were built as separate modules and each was tested on its own.

How it is wired

The mechanism

Why Origin Access Control instead of a public bucket? With OAC, CloudFront signs its requests to S3 and the bucket policy allows only that distribution. The bucket stays private, visitors can't skip the CDN, and nobody can pull objects straight from S3. Setting OAC on the distribution isn't enough on its own — the bucket policy has to say the same thing, which is the first error I hit.

Why API Gateway in front of Lambda? Lambda runs code; it doesn't do API management. API Gateway receives the request, routes the resource and method to the function, and carries the response back. Deploying to a stage gives a stable invoke URL and a snapshot the documentation can be published against.

Why a hand-written inline policy instead of a managed one? The function only ever calls dynamodb:GetItem on one table. AmazonDynamoDBFullAccess would work and break least privilege; AmazonDynamoDBReadOnlyAccess was closer. The inline policy allowing just GetItem on table/UserData is exact.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the console and test results and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

The function "succeeded" while DynamoDB refused it — until the role allowed it

My first test event with a userId reported Executing function: succeeded, but the response body was an AccessDenied error: the code ran fine and DynamoDB blocked it. After giving the role read access, the same test returned the item — email, name and userId.

Method Ran the same JSON test event in the Lambda console before and after the permission change.

Measured

Narrowing to an inline GetItem policy kept it working

I replaced the managed policy with an inline one allowing only dynamodb:GetItem on table/UserData and re-ran the test event. Still succeeded, with the item returned.

Method Re-ran the test event after swapping the policy.

Measured

CloudFront returned AccessDenied until the bucket policy matched OAC

With OAC set on the distribution, the site still returned AccessDenied. Adding the policy the OAC setup generates — s3:GetObject for cloudfront.amazonaws.com, conditioned on my distribution's ARN — made the site load.

Method Loaded the distribution's domain before and after the bucket policy change.

Observed

CloudFront loaded faster than the S3 website endpoint

As an extension I also served the site straight from S3 website hosting and compared load times in the browser; CloudFront was faster, which matches it serving from an edge location near me. I didn't record numbers, so this is an observation, not a benchmark.

Method Compared page loads for both URLs in the browser's network panel.

By design

Visitors can't bypass CloudFront to reach the files

The bucket policy's only grant is to CloudFront for this distribution. I didn't try fetching an object URL directly to confirm the denial once the S3-hosting experiment was cleaned up.

Method Reviewed the bucket policy. Not adversarially tested.

Five claims. three measured, one observed, one stated as a design property rather than dressed up as a result.

What actually broke

Three failures worth keeping

OAC on the distribution, AccessDenied from the bucket

I'd set the distribution's origin access to OAC and expected that to be the whole job. It isn't: the bucket is private by default, and its policy has to grant CloudFront access too. The OAC setup generates that policy; I hadn't applied it.

A successful run with a failure inside it

Lambda's green "succeeded" only means the code didn't throw. The response was DynamoDB's AccessDenied, because the execution role had nothing but CloudWatch logging. Reading the error log is what told me which permission — dynamodb:GetItem — it actually needed.

Turning off Block Public Access didn't make the bucket public

For the S3-hosting comparison I disabled Block Public Access and still got errors. That switch only stops blocking; it doesn't grant anything. A bucket policy statement allowing s3:GetObject to everyone is what opened it.
