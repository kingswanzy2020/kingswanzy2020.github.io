Case study — CI/CD / AWS

A seven-day, AWS-native CI/CD pipeline for a Java web app

Over seven consecutive days I built a delivery pipeline one AWS service at a time — CodeArtifact, CodeBuild, CodeDeploy, CloudFormation — and then joined them in CodePipeline, so a push to main ends with the change live on an EC2 web server.

Guided lab

I built this in my own AWS account as a guided NextWork lab. I'm not pointing you at a live endpoint — the screenshots below were captured during the build, and the CloudFormation template, buildspec.yml, appspec.yml and the deployment scripts in the repo rebuild the pipeline and its web server. Everything below is in the past tense for that reason.

What it does

Summary

The app is a Java web app I generated with Maven on an EC2 development instance and pushed to GitHub. CodePipeline listens for pushes to main through a CodeConnections webhook and runs three stages. Source zips the commit. Build hands it to CodeBuild, which runs buildspec.yml, pulls every dependency through a private CodeArtifact repository, and writes the WAR file to S3. Deploy hands that artifact to CodeDeploy, which runs appspec.yml's lifecycle scripts on an EC2 web server in its own VPC. By day six the whole stack — CodeArtifact, CodeBuild, CodeDeploy, roles and connection — was a CloudFormation template.

How it is wired

The mechanism

Why route dependencies through CodeArtifact? Maven reads pom.xml, and with -s settings.xml it asks CodeArtifact first. CodeArtifact serves what it has and fetches anything new from Maven Central once, then caches it. The build itself only ever talks to a private repository in my account, which needs an authorization token — and getting that token is where day three's first error came from.

Why a separate web server, built from a template? The development instance is where I change code; the web server is what users hit. Keeping them apart means editing one can't break the other. I created the web server's VPC, subnet, route table, internet gateway, security group and instance from CloudFormation, so it can be rebuilt or deleted as one stack.

Why lifecycle scripts? CodeDeploy doesn't know how to run a Java web app; appspec.yml tells it which scripts to run and when. install_dependencies.sh sets up Tomcat and Apache, start_server.sh starts both and enables them on boot, and stop_server.sh stops them cleanly. The CodeDeploy agent on the instance runs them in order.

Why does a rollback only touch the Deploy stage? When I rolled back from CodePipeline, Source and Build kept the newest commit and only Deploy went back to the previous one. The artifact for the old version is still in S3, so going back is a redeploy of a known build, not a rebuild.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the pipeline and the AWS console and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

A push went from GitHub to the live page with no manual step

I changed the app's source and pushed to main. The webhook started a new execution, Source, Build and Deploy all went green, each stage showing the same commit message, and the new line was on the live page when I reloaded it.

Method Pushed a visible change, watched the execution in CodePipeline, then loaded the web server's public DNS name.

Measured

Rolling back the Deploy stage restored the previous page and left Source and Build alone

I started a rollback on the Deploy stage. Afterwards Source and Build still showed the latest commit while Deploy showed the previous one, and the live app was back to its earlier text.

Method Compared each stage's commit message after the rollback, then reloaded the live page.

Measured

A deliberately broken stop script took the automatic rollback down with it

On day five I put systemctll in stop_server.sh with rollbacks enabled. The deployment failed with systemctll: command not found — and so did the automatic rollback, because rolling back starts by running the same broken stop script. Recovery meant fixing the script and deploying a new revision myself.

Method Deployed the broken script and read the deployment history: the failed deployment and the failed rollback.

Observed

The whole stack came up from one CloudFormation template

After two failed attempts (below), the nextwork-devops-stack stack showed all 16 resources — CodeArtifact domain and repositories, CodeBuild project, CodeDeploy application and deployment group, the GitHub connection, roles and policies — at CREATE_COMPLETE.

Method Read the stack's Resources tab.

By design

Builds never fetch directly from a public registry

settings.xml points Maven at CodeArtifact, and CodeArtifact is the one that reaches Maven Central. I didn't block outbound traffic from CodeBuild to prove nothing else is contacted.

Method Reviewed settings.xml and the CodeArtifact upstream configuration.

Five claims. three measured, one observed, one stated as a design property rather than dressed up as a result.

What actually broke

Three failures worth keeping

Two failed builds before CodeBuild produced anything

The first build failed because there was no buildspec.yml — CodeBuild had no instructions at all. The second failed with COMMAND_EXECUTION_ERROR: CodeBuild had the settings.xml pointing at CodeArtifact but no permission to use it, so Maven couldn't resolve a single dependency. Adding an IAM policy for CodeArtifact to CodeBuild's role turned the third build green. Day three had the same shape: the EC2 instance couldn't get a CodeArtifact token until I gave it a role that could.

CloudFormation failed on ordering, then on a circular dependency

My first stack failed because roles and their policies were being created at the same time; a policy needs its role first. I added DependsOn. The second attempt failed with Circular dependency between resources: the roles listed the policies in ManagedPolicyArns while the policies depended on the roles. Removing those references from the roles let CloudFormation create each role, then attach its policies.

A rollback can't save you from the script it has to run

With the typo in stop_server.sh, the deployment failed and the automatic rollback failed for the same reason — it begins by stopping the server with the broken script. The lesson I took from it: rollback protects you from a bad application build, not from broken deployment plumbing.
