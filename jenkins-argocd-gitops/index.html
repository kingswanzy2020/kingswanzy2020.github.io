Case study — Kubernetes / GitOps

A two-repo pipeline where Jenkins never touches the cluster

I split CI and CD across two repositories: Jenkins builds the image, pushes a build-numbered tag to Docker Hub and commits that tag to a manifests repo, and ArgoCD is the only thing that ever applies anything to Kubernetes.

Local cluster

This ran against a local cluster through my own kubeconfig; Terraform created the namespaces and PostgreSQL there before the pipeline's first run. Nothing was exposed publicly. The two repos reproduce it on any cluster with ArgoCD installed, and everything below describes that run.

What it does

Summary

A push to devops-pipeline-app triggered a Jenkins job that built the Flask API with a multi-stage Dockerfile and pushed it to Docker Hub as :BUILD_NUMBER and :latest. Jenkins then cloned devops-pipeline-manifests, rewrote the image line in k8s/deployment.yaml with sed and pushed the commit as Jenkins CI. ArgoCD auto-synced that repo and rolled the two-replica devops-app Deployment in production over to the new tag. The pods reached PostgreSQL in the database namespace, which Terraform had created along with the namespaces.

How it is wired

The mechanism

Why a Git commit as the handoff instead of kubectl apply from CI? If CI ends with kubectl apply, the build server needs a kubeconfig that can write to production, and a compromised job is a compromised cluster. Here Jenkins holds Docker Hub and GitHub credentials and nothing else. Its last stage clones the manifests repo with a github-creds token, changes one line, and pushes. ArgoCD pulls that change in; Jenkins never learns the cluster's address.

Why pin the build number instead of :latest? When every deploy reuses one tag, nobody can say which build is running and a rollback has nothing to go back to. Every build pushes both tags, but the manifest always pins the numbered one, so the manifests repo's history reads as a deploy log — Update image to build 2 — and rolling back is reverting one Jenkins commit while the older image is still on Docker Hub.

Why is the database in its own namespace? The app runs in production and PostgreSQL in database, reached at the fully qualified postgres-service.database.svc.cluster.local through DB_HOST. Splitting them means each can get its own access controls and quotas later without editing the app manifest.

Why does /health query the database? /health runs SELECT 1 and returns 500 if it fails, so it reports whether the app can reach its data, not just whether the process is up. It's built as a readiness target. The image itself is a two-stage build: dependencies installed with --prefix=/install in a builder, only /install copied into a fresh python:3.11-slim, run as a non-root user under Gunicorn with two workers.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the running system and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Observed

Build #2 went from git push to running pods with no manual step

Jenkins build #2 built the image, pushed it and committed the new tag; ArgoCD picked the commit up and rolled the Deployment. Jenkins's commit landed at 19:04:02 and both new pods were running by 19:06:10 — about two minutes from manifest commit to running pods, read off the commit time and the pod ages, not a timed benchmark.

Method Compared the manifests repo commit timestamp against kubectl get pods -n production: 2/2 pods Running 1/1, 0 restarts, 116 seconds old.

Observed

ArgoCD reported Synced and Healthy for both resources

argocd app get devops-app showed the Deployment and the Service both Synced and Healthy, with the manifest pinning devops-pipeline-app:2 rather than :latest.

Method Ran argocd app get devops-app after the rollout.

Observed

The app reached PostgreSQL — under Compose

curl localhost:5000/health returned {"database":"connected","status":"healthy"} when I ran the stack under Docker Compose. In the cluster I saw Terraform's Postgres pod Running with 0 restarts, but the health response itself was captured under Compose, so that's where I'm claiming it.

Method curl against /health under Docker Compose; kubectl get pods -n database in the cluster.

By design

CI holds no cluster credentials

Jenkins's credential store has Docker Hub and GitHub entries and no kubeconfig, and the pipeline never calls kubectl or the ArgoCD API. A compromised build could push a bad tag to Git, which shows up in review history — it couldn't write to the cluster directly. I didn't try to break out of a job to prove it.

Method Reviewed the Jenkinsfile and the Jenkins credentials. Not adversarially tested.

By design

/health fails when the database is gone — untested in the cluster

/health runs SELECT 1 and returns 500 on failure, which is what a readiness probe needs to pull a pod out of the Service. I didn't take PostgreSQL down in the cluster to watch the endpoints change.

Method Read the handler. No outage was simulated.

Five claims. three observed, two stated as design properties rather than dressed up as results.

What actually broke

Two failures worth keeping

ArgoCD said Synced while every pod was failing

The first manifest commit pointed at ahmed3015/devops-pipeline-app:latest before Jenkins had pushed any image. ArgoCD applied it without complaint and showed Synced to 6c083e8, while app health sat at Progressing and both pods were stuck in ErrImagePull. Synced only means the cluster matches Git; Health is what tells you whether the workload runs. Re-syncing couldn't fix it — the pipeline had to deliver a real image first.

Build #1 failed on a template placeholder nobody replaced

The Jenkinsfile was committed with DOCKER_IMAGE = "[[DOCKERHUB_USERNAME=\"ahmed3015\"]]/devops-pipeline-app". Docker rejects brackets in an image name, so the build died before pushing anything. Once it read ahmed3015/devops-pipeline-app, build #2 went all the way through — which is why the first tag in the manifests repo is :2, not :1.
