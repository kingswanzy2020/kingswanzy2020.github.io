Case study — Kubernetes / AWS

Packaging a backend for Amazon EKS with a private ECR registry

I rebuilt the EKS cluster with eksctl, cloned a Flask backend that proxies the Hacker News API, built it into a Docker image on EC2, and pushed it to a private Amazon ECR repository the cluster could pull from.

Guided lab

I built this in my own AWS account as a guided NextWork lab. I'm not pointing you at a live endpoint — the screenshots below were captured during the build, and eksctl, the backend's Dockerfile and three ECR push commands rebuild it from an empty account. What it does

Summary

This was part two of the EKS series. I created the cluster again with eksctl, then cloned nextwork-flask-backend onto the EC2 instance. The backend takes a search query, calls the Hacker News API, formats the result as JSON and returns it. I built it with the project's Dockerfile, created a private ECR repository, authenticated Docker to it and pushed the image as latest, so the cluster had a trusted, private source to pull from instead of a public registry.

How it is wired

The mechanism

Why ECR instead of Docker Hub? ECR is private by default, access is controlled with the same IAM the cluster already uses, and it keeps multiple tags of the same image. For a cluster on EKS that means the nodes pull from a registry in the same account, with no public image dependency in the path.

Why add ec2-user to the docker group instead of using sudo? The Docker daemon runs as root, so ec2-user got a permission error on the first build. Prefixing every command with sudo works, but it means running the whole Docker CLI as root forever. sudo usermod -aG docker ec2-user gives the user permanent access through the group the daemon's socket already trusts.

What's actually in the backend? Three files matter: requirements.txt lists the dependencies, the Dockerfile uses FROM, WORKDIR, COPY, RUN and CMD to build on python:3.9-alpine, and app.py is the API that calls Hacker News and returns JSON.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the running system and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Observed

The image built and landed in a private ECR repository

docker build -t nextwork-flask-backend . finished all five steps on python:3.9-alpine, and the ECR console showed the repository with one image tagged latest, about 40 MB.

Method Read the build output and the ECR repository's Images tab.

Observed

The Docker permission error was fixed at the group, not with sudo

The first build failed because ec2-user couldn't talk to the Docker daemon. After sudo usermod -aG docker ec2-user, Docker commands ran as the normal user.

Method Re-ran the build as ec2-user after the group change.

By design

The cluster pulls the image from ECR — not captured here

The registry exists to be the cluster's image source, and ECR integrates with EKS through IAM. This part of the series ended at the push, so I'm not claiming a pod ran this image.

Method No Kubernetes Deployment was recorded in this part.

Three claims. two observed, one stated as a design property rather than dressed up as a result.

What actually broke

One failure worth keeping

docker build refused to run as ec2-user

The Docker daemon needs root-level access, and the default ec2-user doesn't have it, so the first build hit a permission error. sudo on every command would have worked and stayed wrong. Adding the user to the docker group fixed it permanently.
