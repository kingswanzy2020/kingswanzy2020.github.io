Case study — CI/CD

A Jenkins pipeline that won't containerise code SonarQube rejects

I built a five-stage declarative Jenkins pipeline that builds a Java app with Maven, runs its JUnit tests, sends it to SonarQube, and only builds and pushes a Docker image if the quality gate passes — telling Slack the result either way.

Guided lab

I built this as a NextWork lab and then extended it. I'm not pointing you at a live Jenkins — the screenshots below are from the build, and the Jenkinsfile in the repo rebuilds the pipeline on any Jenkins wired to a SonarQube server, Docker Hub and Slack.

What it does

Summary

A push to cicd-pipeline-app fires a GitHub webhook straight into Jenkins. The Jenkinsfile next to the code checks it out, builds it with Maven, runs the JUnit tests, and sends the code to SonarQube for static analysis. Jenkins then waits for SonarQube's verdict on the quality gate. Only a pass lets the next stage build the Docker image and push it to Docker Hub; a fail aborts the pipeline. JUnit results are published and Slack is notified whatever happened.

How it is wired

The mechanism

Why does the pipeline live in a Jenkinsfile? Because then a change to the pipeline is a commit next to the code it builds, reviewed the same way. Nothing about how this project gets built lives only in the Jenkins UI.

Why make the quality gate abort the pipeline? A gate that only reports is a suggestion. Jenkins waits for SonarQube's webhook with the gate result, and with abortPipeline: true a failed gate stops the run before the Docker stage. Code that fails analysis never becomes an image, so it can't reach the registry by accident.

Why publish test results in post { always }? If JUnit publishing sits inside the test stage, a failing test can end the stage before its report is saved — and the run where tests failed is exactly the one whose report you need. In the post { always } block the reports are published on every run, pass or fail. Slack goes in the same place for the same reason.

Why did SonarQube need kernel settings? SonarQube embeds Elasticsearch, which needs more memory maps and file handles than a default Linux host allows. I set vm.max_map_count=262144 and fs.file-max=131072 before starting it. The SonarQube token and Docker Hub credentials live in Jenkins's credential store, not in the repo.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the pipeline runs and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

A test I broke on purpose reached Slack as a failure

I broke a unit test deliberately and pushed. The pipeline failed, the JUnit report for the failed run was still published, and the failure alert arrived in Slack. That's the end-to-end check for the notification path, not just the configuration.

Method Pushed a deliberately failing test, then read the Jenkins run, its test report and the Slack channel.

Observed

All five stages went green, and the analysis showed up in SonarQube

On a clean commit the stage view showed checkout, build, test, analysis and the Docker stage all passing, and the project appeared in SonarQube with its quality gate result.

Method Read the stage view in Jenkins and the project page in SonarQube (screenshots below).

By design

A failed quality gate stops the image from being built — not forced

The gate step waits for SonarQube's webhook and runs with abortPipeline: true, which ends the pipeline before the Docker stage. I didn't commit code designed to fail the gate, so this is what the step guarantees rather than a block I watched happen.

Method Reviewed the gate stage in the Jenkinsfile. Not tested with failing code.

By design

No credential lives in the repository

The SonarQube token and Docker Hub login are referenced by ID from Jenkins's credential store. I didn't audit the history of every file, so this is a property of how the pipeline was written.

Method Reviewed the Jenkinsfile's credential references.

Four claims. one measured, one observed, two stated as design properties rather than dressed up as results.

One failure worth keeping

A test I broke on purpose, to find out who would hear about it
