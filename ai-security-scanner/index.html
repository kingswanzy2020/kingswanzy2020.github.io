Case study — AI × Security

An AI security scanner for Python, with severity you can see

I built a command-line scanner that sends Python source to Gemini with a structured security prompt and prints each finding — vulnerability type, why, impact and a secure fix — colour-coded by severity, so the critical one is the first thing you read.

Local script, not a service

This is a script you run against a file, not a hosted tool. python scanner.py with a Gemini key in .env reproduces everything below.

What it does

Summary

scanner.py reads a Python file, sends it to Gemini with a prompt that requires four fields for every finding — the vulnerability type, why it's vulnerable, its impact, and a secure code fix — and a severity rating. An add_colors_to_output function then colours the response by severity with colorama. I ran it against deliberately vulnerable samples covering three classes that professional SAST tools look for: SQL injection, hardcoded credentials, and weak MD5 hashing.

How it is wired

The mechanism

Why a structured prompt? "Find security issues" gets a vague essay. Requiring the same four fields per finding makes every answer actionable — you know what's wrong, why it matters, and what to write instead — and makes the output predictable enough to colour by severity.

Why colour by severity? When a file has several findings, the order you read them in matters. CRITICAL in red is the first thing your eye lands on.

Why .env for the key? A security scanner with a hardcoded API key would flag itself. The key is loaded from .env, which stays out of the repository.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the scanner's output and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

All three seeded vulnerability classes were found, with fixes

Against the vulnerable samples, the scanner reported the SQL injection (the username concatenated into the query, fixed with a parameterised query), the hardcoded password, and the weak MD5 hashing, each with an impact and a secure rewrite.

Method Ran python scanner.py against each sample and read the findings.

Observed

Severity came out colour-coded

With colorama in place, the SQL injection printed as SEVERITY: CRITICAL in red, ahead of its description and fix.

Method Read the terminal output after adding the colouring function.

Observed

The connection worked before any scanning

A test call returned "Hello, security scanner!", which confirmed the key from .env was being sent and accepted.

Method Ran the connectivity check in scanner.py.

By design

Findings are a model's opinion, not a proof

An LLM can miss a vulnerability or invent one. I tested three known classes on purpose-built samples; I didn't measure false positives or false negatives on real code.

Method No precision or recall measurement was done.

Four claims. one measured, two observed, one stated as a design property rather than dressed up as a result.

What actually broke

One failure worth keeping

The SDK was deprecated under me

Every run printed a FutureWarning: support for google.generativeai has ended and it won't get updates or fixes; switch to google.genai. The scanner worked, but on a package with no future. The later PR reviewer uses google-genai; this script hasn't been moved yet.
