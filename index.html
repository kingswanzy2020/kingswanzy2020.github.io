Case study — Kubernetes

Production application on Amazon EKS

I put a three-tier app on a two-node EKS cluster where the DNS record, the TLS certificate, the storage and the autoscaling were provisioned by controllers reacting to Kubernetes resources — not by me, clicking around in the AWS console.

Decommissioned

I decommissioned the cluster after validation; the eksctl and Helm config reproduces it in under 30 minutes. The public endpoint isn't live anymore, and everything below is written in the past tense because the cluster is gone, not because it never existed.

What it does

Summary

An nginx frontend, an httpbin API and a PostgreSQL database ran together on a two-node Amazon EKS cluster, reachable over HTTPS on a domain delegated to Route 53. The DNS record, the certificate, the load balancer and the persistent volume weren't created by hand — each one was provisioned by a controller reacting to a Kubernetes resource. The frontend scaled on measured CPU, the database survived rescheduling on an EBS volume, and every controller ran under its own IAM role instead of the node's.

How it is wired

The mechanism

Why does a controller write the DNS record instead of me? The domain was delegated from Porkbun to a Route 53 hosted zone, which made AWS authoritative for its records — that authority is the precondition for everything else here. From there, external-dns watches Ingress resources and writes the A record itself, the AWS Load Balancer Controller reads the same Ingress and provisions a real ALB with path-based routing (/ to the frontend, /api to the API, both through one load balancer), and cert-manager requests the certificate. None of that involved opening the AWS console.

Why DNS-01 instead of HTTP-01? HTTP-01 needs a working ALB to prove ownership of the domain the ALB is supposed to serve — a chicken-and-egg problem the first time anything gets provisioned. DNS-01 validates before the domain resolves to the cluster at all, and it leaves wildcard certificates available later if I need them.

Why WaitForFirstConsumer on the volume? The PersistentVolumeClaim provisions an EBS gp3 volume through the CSI driver, and the StorageClass is set to WaitForFirstConsumer, so the volume isn't created until a pod has claimed it and been scheduled. That ordering is what keeps the volume in the same Availability Zone as the node that needs it — provisioning it any earlier risks landing it in the wrong AZ, where the pod could never reach it. metrics-server feeds a HorizontalPodAutoscaler that adds frontend replicas on measured CPU, and kube-prometheus-stack scrapes the cluster into Grafana. Grafana persistence was left off on purpose — the dashboards are declarative, and the cluster was never meant to outlive this project.

Why does each controller get its own IAM role instead of using the node's? eksctl created the cluster with an OIDC provider, which is what makes IRSA possible in the first place: each controller's service account assumes its own role, so no controller borrows the node instance profile, and a compromised pod only inherits that one controller's permissions instead of everything the node can do. The application itself runs under scoped Roles in its own app namespace rather than anything cluster-wide.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the running cluster and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

The frontend autoscaled on real CPU, then scaled back down

The HorizontalPodAutoscaler was set to a floor of 2 replicas, a ceiling of 10, and a 50% CPU target measured against the pod's request. Under generated load it added a third replica once frontend CPU hit 60%, and dropped back to 2 replicas once the load stopped. The ceiling of 10 is just the configured limit — 3 is as far as the test actually pushed it.

Method Generated load against the frontend, then watched kubectl get hpa through the scale-up and scale-down, cross-checking per-pod CPU in Grafana to confirm the third replica was actually taking traffic.

Measured

TLS was issued end-to-end without me touching anything

cert-manager completed a DNS-01 challenge against the Route 53 zone, and the Certificate resource reported READY=True after 38 minutes. Renewal runs through the same controller loop, so it doesn't depend on me remembering to do anything.

Method Watched the Certificate, CertificateRequest and Order resources through issuance to READY=True. Elapsed time came from the resource timestamps, not a guess.

Observed

Nothing got clicked in the AWS console after the cluster was created

After eksctl create cluster, the DNS records, the certificate and the load balancer were all created by controllers responding to Kubernetes resources. I held to that as a rule for the whole build, mostly because infrastructure that only exists because someone remembers which buttons they clicked can't be rebuilt in 30 minutes — and reproducibility was the actual point of the exercise.

Method Traced the ALB, the Route 53 A records and the certificate each back to the Kubernetes resource that caused them — the Ingress, the external-dns annotation, the Certificate object.

By design

The data tier is bound to an EBS volume so it outlives the pod — untested

PostgreSQL claims an EBS gp3 volume through the CSI driver, and the StorageClass binds WaitForFirstConsumer, so the volume only gets created once a pod has claimed it and been scheduled — which puts it in the same Availability Zone as its node instead of stranding it somewhere the pod can never reach. That's what the configuration guarantees. I never actually deleted the pod and re-queried the data, so what I'm claiming here is the binding, not the recovery.

Method Confirmed PVC binding and AZ placement. No restart test was run — persistence across rescheduling is an expectation from how the volume is bound, not something I measured directly.

By design

Each controller held its own IAM role, not the node's

The cluster was created with an OIDC provider, and IRSA binds the AWS Load Balancer Controller, cert-manager and external-dns each to their own service account and IAM role. In theory that means a compromised controller pod only inherits that controller's permissions, not everything attached to the node. That's a property of how the roles and trust policies are written — I didn't try to break it.

Method Reviewed role and trust-policy configuration per service account. Not adversarially tested.

By design

Rolling updates were gated on readiness probes

The frontend and API expose liveness and readiness on different paths, since nginx and httpbin answer health checks differently. Liveness restarts a container that's wedged; readiness keeps a pod out of the Service until it can actually serve, which is the actual mechanism that stops a rolling update from dropping requests. I didn't measure request loss across an actual rollout, so this is a property of the deployment spec, not a zero-downtime number I can point to.

Method Reviewed probe configuration and rollout behavior. No load was held across a rollout to count failed requests.

Six claims total. Two measured, one observed, three stated as design properties rather than dressed up as results.

What actually broke

Two failures worth keeping

PostgreSQL crash-looped on a brand-new EBS volume

initdb refused to run because /var/lib/postgresql/data "exists but is not empty." Turns out the EBS filesystem root always carries a lost+found directory, and Postgres won't initialize into a directory that isn't empty. Fixed by pointing the data directory at a subdirectory of the mount point instead of the mount point itself.

The ALB served nothing while the controller logged no certificate found for host on every reconcile

The Ingress itself was fine. The certificate just hadn't been issued into the right namespace yet. Good reminder that with controller-driven infrastructure, "the resource exists" and "the resource is ready" are two different states — and the reconcile loop will keep telling you which one you're in, once a second, until you fix it.
