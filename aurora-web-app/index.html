Case study — AWS / Databases

A PHP web app on EC2 writing to Amazon Aurora

I provisioned an Aurora MySQL cluster together with the EC2 instance that talks to it, put an Apache and PHP app on the instance that writes form input to the database, and checked every write a second time from the MySQL command line.

Guided lab

I built this in my own AWS account as a guided NextWork lab. I'm not pointing you at a live endpoint — the screenshots below were captured during the build, and the cluster settings and the PHP page rebuild it. This page covers both parts of the lab: the database and its host, then the app. Everything below is in the past tense for that reason.

What it does

Summary

I started creating an Aurora cluster, stopped halfway to launch the EC2 instance it would serve — with a new key pair, a public IP and its own security group — and then finished the cluster with Connect to an EC2 compute resource pointed at that instance. On the instance I installed Apache, PHP, php-mysqli and the mariadb105 client, put the connection details in dbinfo.inc, and wrote a sample PHP page that inserts a name and address and lists every row. Then I logged into the database with the MySQL CLI and checked the tables and rows directly.

How it is wired

The mechanism

Why stop halfway through creating the database? The cluster's connectivity settings want a compute resource to connect to. Launching the instance first meant I could pick it, and RDS added a security group to each side with an inbound rule letting that instance — and only that instance — reach the database.

Why Aurora rather than MySQL on the instance? Running MySQL on the VM means owning patching, replication, failover and backups. Aurora keeps MySQL compatibility and hands those to AWS; a cluster has a writer and can add readers that spread SELECT load. This build used the Dev/Test template, so I'm describing the topology Aurora offers, not a replica I load-tested.

Why check the data with the CLI when the page already shows it? The page displaying a row only proves the page and the database agree with each other. Logging in with the MySQL client and running SHOW DATABASES, USE sample and SHOW TABLES checks the data where it actually lives.

Why dbinfo.inc? It keeps the endpoint, user and password out of the page code. It doesn't make them secret — it's still a plaintext file on the instance. Secrets Manager would be the next step; this lab stops at separation.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the page and the database and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

Rows written by the page showed up in the database

I added entries through the form; the page listed them with IDs 1 to 3. Logged in with the MySQL CLI, the sample database was there with an EMPLOYEES table holding the same rows.

Method Submitted the form, then SHOW DATABASES, USE sample, SHOW TABLES and a query in the CLI.

Observed

SSH only worked once the key was owner-read-only

ssh -i with the new key pair connected after I removed all permissions for group and others on the key file.

Method Connected from my terminal to the instance's public address.

Observed

RDS wired the two security groups itself

Choosing Connect to an EC2 compute resource and picking the instance made RDS add a security group to the instance and one to the database, with an inbound rule allowing the instance.

Method Read the connectivity settings during database creation.

By design

Nothing else can reach the database

The database's inbound rule names the instance's security group. I didn't try connecting from anywhere else.

Method Reviewed the security group rules. Not adversarially tested.

Four claims. one measured, two observed, one stated as a design property rather than dressed up as a result.

What actually broke

One failure worth keeping

The database wanted a server that didn't exist yet

Halfway through creating the cluster, the connectivity step needed an EC2 instance to connect to. I stopped, launched the instance with its own key pair and security group, and came back. In hindsight it's the right order anyway: the database exists to serve something.
