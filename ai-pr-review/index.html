Case study — CI/CD / AI

AI pull-request review with Gemini in GitHub Actions

I built a workflow that sends every pull request's diff to Gemini with a structured reviewer prompt, posts the review as a PR comment, and labels the PR Critical, Warning or Good from a machine-readable severity line.

CI workflow

This is a workflow in a repository, not a hosted bot. It runs on GitHub's runners whenever a pull request against main is opened or updated. Everything below describes the PRs I opened to test it.

What it does

Summary

ai_review.py takes a diff and asks Gemini to review it as a code reviewer, returning a summary, security issues, bugs, performance notes, a score and a fix for each finding. I tested it locally against a sample diff first. The workflow checks out the PR with full history, generates the diff, runs the script with the key from GitHub Secrets, and posts the result with github-script. As an extension, the prompt also asks for a single SEVERITY_SUMMARY line that the workflow parses to apply one of three labels.

How it is wired

The mechanism

Why test the script locally before automating it? If the prompt or the parsing is wrong, a workflow just makes the wrong answer arrive faster. I ran ai_review.py against sample_diff.txt first and checked it found the SQL injection the sample was built around before wiring it to pull requests.

Why a SEVERITY_SUMMARY line? Free-text reviews are for people; a workflow needs one thing it can parse. Asking the model for a single machine-readable line means the label step doesn't have to interpret prose, and a reviewer can sort open PRs by label without opening them.

Why GitHub Secrets for the key? The key authenticates every request against my quota. In a public repository it would be both a cost and an access risk, so it lives in Secrets and reaches the script as an environment variable.

Why does the job only get pull-requests: write? It needs to read code and write a comment and a label, and nothing else. The workflow's permissions block says exactly that.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the pull requests and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

The script found the SQL injection in the sample diff before any automation

Run locally against sample_diff.txt, the review flagged the get_user function for building its SQL query with an f-string from the username — a SQL injection — and also called out the database connection never being closed.

Method Ran python scripts/ai_review.py scripts/sample_diff.txt and read the output.

Measured

A PR with shell=True on user input was flagged High and labelled Critical

I opened a PR adding dangerous.py, which passes user input to subprocess.call(..., shell=True). The workflow's comment led with a shell injection finding at severity HIGH, and the PR got the Critical label.

Method Opened the test PR and read the bot's comment and the applied label.

Observed

It flagged my own script too

The reviewer pointed at a shell-injection path and a hardcoded-key risk in my own code. I fixed both — the shell interpreter off, the key moved to an environment variable — and the re-review no longer raised them.

Method Read the review on the PR before and after the fix.

By design

The key never appears in the repository

It's read from GitHub Secrets as an environment variable in the job. I didn't audit every log line for masking failures; GitHub masks registered secrets in logs.

Method Reviewed pr-review.yml's env block.

Four claims. two measured, one observed, one stated as a design property rather than dressed up as a result.

What actually broke

One failure worth keeping

Building the workflow was harder than the script

The script worked locally on the first real run. Wiring it into a pull-request workflow — checkout depth, getting the diff into the script, posting through github-script — took most of the four hours. The model was the easy part.
