Case study — AWS

A static website on S3, with the access model done deliberately

I served a website straight from an S3 bucket in Seoul, worked through the 403 Forbidden that every first attempt hits, and added a bucket policy that refuses to delete the site's index.html — even for me.

I built this in my own AWS account as a guided NextWork lab. I'm not pointing you at a live endpoint — the screenshots below were captured during the build, and the site files in the repo, a bucket and one policy recreate it. Everything below is in the past tense for that reason.

What it does

Summary

I created the bucket in Seoul, the region closest to me, uploaded index.html and a folder of assets, and turned on static website hosting with index.html as the index document. That produced a bucket endpoint URL — which returned 403 Forbidden, because objects are private by default. I disabled Block Public Access, enabled ACLs and made the objects public, and the site loaded. Then I added a bucket policy denying deletion of index.html and tried to delete it myself.

How it is wired

The mechanism

Why did the endpoint return 403 at first? Enabling website hosting doesn't make anything public. Every object was still private, and Block Public Access was on as the first layer. Turning that off only stops blocking — something still has to grant read access, which here was a public-read ACL on the objects.

ACLs or a bucket policy? ACLs are per object: good for granting read on specific files. A bucket policy is one JSON document for the whole bucket, saying who can do what to which objects. I used ACLs for the public read and a bucket policy for the guardrail.

Why a policy that blocks the owner? An explicit Deny applies to every principal, including the account that owns the bucket. A deny on deleting index.html turns an easy mistake — deleting the page that is the site — into one that has to be undone on purpose first.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the bucket and its endpoint and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

The endpoint went from 403 to the live site

The first visit to the bucket endpoint returned 403 Forbidden (AccessDenied). After turning off Block Public Access, enabling ACLs and making the objects public, the same URL served the site.

Method Loaded the endpoint URL before and after each change.

Measured

The policy stopped me deleting index.html

I tried to delete index.html from the console as the bucket owner. S3 reported Failed to delete: 1 object, with Access denied as the error.

Method Attempted the delete in the console after attaching the policy.

By design

Only reads are public

The ACLs grant public read; nothing grants public write. I didn't try writing anonymously to confirm it's refused.

Method Reviewed the object ACLs. Not tested.

Three claims. two measured, one stated as a design property rather than dressed up as a result.

What actually broke

One failure worth keeping

403 Forbidden on a bucket I'd just made a website

Website hosting and public access are separate switches. Hosting was on; every object was still private, and Block Public Access was still on above them. I turned off the block, enabled ACLs and granted public read per object — deliberately, one layer at a time, instead of opening the whole bucket.
