Case study — AWS / Containers

Sharing container images across AWS accounts without sharing an account

With a project buddy on a second AWS account, I pushed a Docker image to my private ECR repository and granted their account just enough access to pull and deploy it on Elastic Beanstalk — and they did the same for me.

Guided lab

This was a two-person NextWork lab across two AWS accounts. I'm not pointing you at a live endpoint — the screenshots below were captured during the build, and the Dockerfile, page and Dockerrun.aws.json in the repo plus two repository policies rebuild it. Everything below is in the past tense for that reason.

What it does

Summary

Each of us built an nginx image with our own index.html, created a private ECR repository, authenticated Docker with aws ecr get-login-password, and pushed. Then each of us deployed the other person's image on Elastic Beanstalk, using a Dockerrun.aws.json that names the image in the other account and exposes port 80. Nothing was shared but ARNs: every grant is a statement in a repository policy naming exactly who may pull.

How it is wired

The mechanism

Why repository policies instead of sharing credentials or a public repo? Sharing credentials collapses the boundary between accounts; making the repository public hands the image to everyone. A repository policy grants pull access to specific principals in another account and nobody else, and it's written down where it can be reviewed.

Why did the policy need two kinds of principal? Two different things pull the image. I pull it from my terminal as an IAM user, so my user's ARN has to be allowed. Elastic Beanstalk's EC2 instance pulls it during deployment under its instance role — a different principal that needs its own grant. The first fix covered only the first.

What does Dockerrun.aws.json do? It tells Elastic Beanstalk to run a pre-built image instead of building one: version 1, a single container, the image's full ECR URI in the other account, and container port 80.

Why does CPU architecture matter here? Images are built for one architecture — x86-64 on most laptops and servers, ARM64 on Apple silicon and Graviton. If the person building and the host running differ, the image won't run. docker buildx with --platform linux/amd64,linux/arm64 builds one image for both.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the consoles and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

Pulling across accounts failed with 403 until the policy named me

My first docker pull of my buddy's image returned 403 Forbidden, because their repository is private. After we each added the other's IAM user ARN to our repository policies, the pull worked.

Method Ran docker pull against the other account's repository before and after the policy change.

Measured

Beanstalk couldn't reach the image until its role was named too

With the user ARNs in place, my environment still showed This site can't be reached: the instance pulling the image wasn't my IAM user. We added the Beanstalk and EC2 instance role ARNs to both policies, rebuilt the environments, and both sites came up running the other person's page.

Method Opened the environment URL, changed the policies, rebuilt, and opened it again.

Observed

The image landed in a private repository

After the push, my repository listed the image, tagged latest.

Method Read the repository's Images tab.

By design

Each grant is explicit and auditable

Every cross-account permission is a statement in a repository policy naming specific ARNs, so the policy is the complete list of who can pull. I'm stating that from the policies; I didn't try pulling from a third account.

Method Reviewed both repository policies. Not tested from an unlisted account.

Four claims. two measured, one observed, one stated as a design property rather than dressed up as a result.

What actually broke

Two failures worth keeping

403 Forbidden on the first pull

Private means private: without a repository policy naming my IAM user, my buddy's ECR refused me, and mine refused them. Adding each other's user ARN fixed the manual pull.

The site couldn't be reached — the permission was on the wrong principal

The environment launched and the URL didn't load. The repository policies only allowed our IAM users, but it's the Beanstalk instance that pulls the image, under its own role. Adding the instance and Beanstalk role ARNs and rebuilding fixed it. Two different 403s for one image, because two different things were pulling it.
