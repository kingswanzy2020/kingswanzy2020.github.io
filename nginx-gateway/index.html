Case study — Networking

An NGINX traffic gateway where balancing and caching show up in the log

I ran one NGINX process as a public gateway and both of its own upstream backends, so round-robin balancing, a cache MISS-to-HIT transition and a deliberate 502 all show up in a single access log — with no containers, no root and no port below 1024.

Local lab, not a service

This is a lab that runs from a cloned directory with nginx -p "$PWD", not something deployed. The commands under Source reproduce every log line below on any machine with NGINX installed.

What it does

Summary

A request to :8080/ is served from the gateway's own document root. A request to /app/ goes through proxy_pass: the cache is consulted first, and on a MISS the request goes to backend_pool, which alternates between backend-a on :8081 and backend-b on :8082 — sibling server blocks in the same config, each stamping its own X-Backend header. A third path points at :8999, where nothing listens. A custom log format prints upstream= and cache= on every line, so all of it can be read in one place.

How it is wired

The mechanism

Why put upstream= and cache= in the log? Stock NGINX logs show neither, which is why the interaction between balancing and caching is normally invisible. Once a response is cached, upstream= goes empty and the alternating backends stop alternating. With both fields on every line, that reads as the cache working instead of the pool breaking.

Why override Cache-Control, and only on /app/? Both backends send Cache-Control: no-store, and NGINX honours it by caching nothing — cache=MISS forever, with no warning. proxy_ignore_headers Cache-Control scoped to /app/ lets the cache be exercised there while leaving the gateway's own responses honest.

Why the backends in the same file? In production they'd be separate hosts. Collapsing them into one config trades realism for legibility: the whole request path, both ends of it, is one file read top to bottom.

Why break it on purpose? A 502 looks the same in the browser whether the upstream is down, unreachable or never existed. Pointing a path at a port with no listener gives a failure whose cause I already know, so I can learn what the error log says about it.

What I verified, and how

Evidence, separated from design intent

Building something and being able to prove it works are different claims, so I've kept them separate below. Measured means I created the condition myself and recorded what happened. Observed means I looked at the access and error logs and saw the state it was already in. By design means the configuration guarantees it, but I didn't run a test against it — better to say that plainly than dress it up as a result.

Measured

The 502 traced to the cause I planted

Requests to /broken/ returned 502 Bad Gateway from nginx/1.31.5 while the gateway itself stayed healthy on :8080. Hitting 127.0.0.1:8999 directly in a browser failed to connect, and the error log recorded the refused connection — no listen 8999 anywhere in the config.

Method Requested /broken/, browsed :8999 directly, and read the error log.

Measured

The cache went MISS to HIT once Cache-Control was overridden

Before the override, every /app/ request logged cache=MISS. With proxy_ignore_headers Cache-Control on /app/, the log showed the MISS, then cache=HIT with upstream= empty from that line on.

Method Repeated curl localhost:8080/app/ before and after the change, reading the access log.

Observed

The pool alternated strictly between the two backends

Consecutive /app/ requests on a cold cache logged upstream= alternating 8081, 8082, 8081… under NGINX's default equal weighting.

Method Read upstream= across consecutive access-log lines.

By design

Config errors never reach a running listener

I ran nginx -t before every start and reload, so a syntax error fails at validation instead of on a live reload. That's a habit I kept, not a failure I induced to prove it.

Method Validated with nginx -t -p "$PWD" before each start and reload.

Four claims. two measured, one observed, one stated as a design property rather than dressed up as a result.

Proof

From the logs and the browser

What actually broke

Three failures worth keeping

cache=MISS on every request, forever

The cache was configured correctly and doing nothing: both backends answer Cache-Control: no-store, and NGINX honours that by not storing the response. Neither log said why. proxy_ignore_headers Cache-Control on /app/ fixed it, and HITs appeared immediately.

Load balancing "stopped working" the moment caching started

Once responses came from cache, upstream= went empty and the 8081/8082 alternation vanished. That reads exactly like a broken pool. It's the cache doing its job — a HIT never touches a backend, so there's no upstream to log. Recognising that as expected behaviour was the real lesson of the build.

A 502 that had nothing to do with the gateway

The browser said Bad Gateway while the gateway was perfectly healthy. Only the error log said where it failed: connection refused on :8999. The browser tells you that it failed; the error log tells you where.
